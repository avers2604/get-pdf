# GD-31J.21 — нативная UNO-проверка сохранения и SHA-256-квитанция

**Дата:** 29.10.2026. **База:** GD-31J.20 Draft PR #92. **Статус:** изменения подготовлены; C# MSTest, Python unittest, реальный Python/UNO, GUI и SMB **не запускались**. Поставка не готова к выпуску.

## Механика

**GD-31J.20**: .NET контролирует размер, mtime UTC и SHA-256 открытого документа, перед обычным сохранением проверяет исходник, а при конфликте показывает кнопку создания отдельной копии.

**GD-31J.21**: протокол `EditorDocument.SaveAsync` дополнен проверяемым **ожидаемым** SHA-256:

1. После .NET preflight `OfficeRevisionSaveCoordinator` передаёт ожидаемый хеш в отдельный локальный `lo_editor.py` как `expectedSha256`, без отправки во внешние системы.
2. Нативный процесс Python/UNO читает **свой** `Document.source_path` (установлен только из исходного `op_open`, не из параметра команды save), вычисляет полный SHA-256 и **до** вызова UNO `store()` сравнивает его с ожидаемым значением. Размер чтения ограничен 256 МиБ. Неверная форма SHA ⇒ fail closed.
3. Различие ⇒ `GETDOC_SAVE_CONFLICT` и нулевое число попыток UNO `store()` для этого запроса. В .NET ошибка преобразуется в `OfficeFileConflictException`; отдельный диалог/панель из GD-31J.20 предлагает сохранить редакцию копией.
4. После успешного `store()` нативный мост заново хеширует **исходный путь** и возвращает `sha256` в ответе. Отсутствующая/некорректная квитанция не признаётся сохранением.
5. .NET повторно читает свой источник, сверяет SHA квитанции с фактически прочитанным содержимым и **только после совпадения** обновляет baseline и событие `ModifiedChanged`. При несовпадении baseline не продвигается; аварийная копия не должна удаляться по ложному успеху.

## Проверки, пока только исходники

- `OfficeFileRevisionGuardTests` дополнены ошибочной, отсутствующей и успешной native-квитанцией. Существующие сценарии: атомарная замена, удаление, same-size/same-mtime, failed store, отказ от вызова native при stale baseline.
- `scripts/tests/test_lo_save_receipt_contract.py`: без импорта UNO извлекает реальную функцию `getdoc_file_sha256` из AST; тестирует изменение того же размера с восстановленной временной меткой и проверяет порядок операций в `op_save`.
- `scripts/office_acceptance.py`: обязательный локальный preflight `office-native-save-receipt-contract-tests`, закреплённый тестом сценария. Сборка и интеграционная проверка остаются в будущем локальном acceptance.
- Ручной gate из GD-31J.20 остаётся: две машины/учётные записи с одной SMB-шарой, одновременные изменения, Ctrl+S, восстановление, сохранение копий, проверка фактических файлов без скрытых перезаписей.

## Не путать с полной безопасностью

Это **двухступенчатая оптимистическая проверка**, а не атомарная транзакция и не универсальная блокировка SMB. Изменение возможно *после* повторного native hash и *до/во время* UNO `store()`. Никакая SHA-квитанция сама по себе не гарантирует, что исходный файл нельзя подменить позднее. Для GUP-2/WORM и Nextcloud нужен реальный server-side CAS с авторизованным commit/immutable revision, а для обычного SMB — отдельно проверенные OS/SMB locking или соглашение на сохранение новой версии.

**EuroOffice DesktopEditors CEF, Windows/X11 OSR, IME, clipboard и полноценное редактирование через официальный EuroOffice native API не реализованы этой цепочкой.** Пользовательский движок здесь — ограниченный LibreOffice/UNO fallback, пока нативный EuroOffice остаётся изолированной лабораторией.

Следующий реальный gate — собрать код, запустить Python unittest и MSTest, затем GUI/SMB проверки на автономном стенде. По текущему решению пользователя проверки отложены и автоматически не запускаются. `main` и GitHub Actions не менялись.
