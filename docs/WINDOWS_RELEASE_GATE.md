# ГЭТ PDF — Windows offline build and MSI gate

`scripts/windows-build-msi.ps1` выполняется **только на Windows** в подготовленном стенде. Требуются .NET SDK 10, WiX Toolset 5 и доступ к проверенным локальным NuGet-пакетам. Автоматические GitHub Actions не используются.

```powershell
pwsh -File .\scripts\windows-build-msi.ps1 -OfflineNuGetFeed 'D:\ApprovedNuGet'
```

Сценарий последовательно выполняет restore, build, MSTest, удаление старой папки publish, самостоятельную публикацию для win-x64 и проверку на ошибочно попавшие scanner/driver worker. WiX собирает отдельный per-machine MSI; регистрируется **только доступность ГЭТ PDF для .pdf**, не изменяется UserChoice. Отдельный UpgradeCode предотвращает конфликт с GUP-Scan.

Подпись необязательна при исследовательской сборке, но для выпуска нужна подтверждённая цепочка доверия. Для внутреннего сертификата:
```powershell
pwsh -File .\scripts\windows-build-msi.ps1 -OfflineNuGetFeed 'D:\ApprovedNuGet' -SignToolPath 'C:\SDK\signtool.exe' -SigningThumbprint 'CERTIFICATE_SHA1_THUMBPRINT'
```

**Статус:** сценарий и WiX-описание добавлены в исходники, но в текущем окружении НЕ исполнялись. Факт успешной Windows-сборки, MSBuild/WiX совместимость, установка/обновление/удаление MSI, запуск PDF, подписи и печать ещё не подтверждены. `release-manifest.json` формируется только после успешного локального gate и не является актом аппаратной приёмки.

Проверить дополнительно: EXE/desktop runtime и целостность всего payload, создание ярлыка, ассоциацию «Открыть с помощью», сохранение выбора пользователя, установку и удаление рядом с GUP-Scan, x64 и фактическое время печати. Сервисов и доступа к интернету приложение не требует.

**Важно:** установщик `ГЭТ PDF` не имеет права удалять драйверы сканера, профили GUP-Scan или документы пользователя.

## Дополнительные обязательные этапы для выпуска

- Выполнить реальный `dotnet build` и `dotnet test`, затем проверить 10–16 WPF-вкладок и передачу страниц с Undo/Redo.
- Проверить на Windows отображение кириллицы во внешнем PDF-reader после заполнения AcroForm и отказ на signed/XFA/JavaScript.
- Проверить настоящие подписи и цепочки с локальными УЦ, CRL/OCSP, GOST/CryptoPro; текст результата не должен неверно подтверждать юридическую КЭП.
- Печать на конкретных драйверах ГЭТ: A3/A4, ду́плекс, копии, ориентация, 200/300/600 DPI, отмена и spooler. Текущий raster pipeline **НЕ** соответствует требованию о векторной печати.
- Проводить установку/обновление/удаление MSI на тестовой Windows VM, без сканеров и GUP-Scan. Сверить SHA-256 и подпись.
- Только после прохождения каждого этапа можно выпускать сборку. Значения `releaseApproved` и `wpfHardwareValidated` в manifest не должны выставляться автоматически.


## Дополнительная приёмка локального статуса и обновлений

- Включить `ExportGetSystemStatus=true` в политике и проверить атомарный JSON при открытии/закрытии 1–16 вкладок, отсутствие путей/текста PDF; выключить и убедиться, что сетевых запросов нет.
- Испытать `windows-check-offline-update.ps1` на действительной подписанной MSI, повреждённом SHA, чужом сертификате, неправильном UpgradeCode и попытке downgrade; ни один случай не должен запускать MSI.
- Проверить закрытие WPF вкладки при занятой очереди PDFium: отмена должна прерывать ожидающих импортеров и не обновлять старые миниатюры. Native PDFium память и результат работы с архивными документами фиксировать отдельно.

## Ручной запуск WPF после сборки

После локального `windows-build-msi.ps1` проверить запуск на тестовой
Windows-машине:

```powershell
# Выполнить внутри интерактивного PowerShell 7 (pwsh):
.\scripts\windows-smoke-viewer.ps1 `
  -PdfPaths @('C:\Samples\a.pdf', 'C:\Samples\b.pdf') `
  -EvidenceFile '.\dist\release\smoke-launch.json'
```

Скрипт запускает `GetPdf.exe` с 1–16 PDF и ждёт появления окна.
Он **не** утверждает, что страницы отображаются правильно, не нажимает
кнопки, не печатает, не изменяет PDF и не закрывает процесс.

Свидетельство содержит только версию схемы, время, SHA-256 EXE,
количество открываемых файлов и PID. **Пути и имена PDF не записываются.**
Все флаги `windowsUiAccepted`, `realPrintingValidated`,
`msInstallerValidated` и `releaseApproved` установлены в `false`.

После открытия вручную выполнить сценарии из
`docs/SPLIT_ACCEPTANCE.md` и `docs/PDF_TABS_ACCEPTANCE.md`.
Если окно не появилось, скрипт завершится ошибкой, а основной release
gate остаётся незавершённым.

## Дополнительный этап печати PDFium/GDI

- По умолчанию `AllowNativeGdiPrinting=false`; обычная WPF raster-печать должна продолжать работать независимо от нового native DLL.
- В тестовом образе Windows с разрешённой политикой отдельно проверить PDFium `FPDF_LoadDocument` / `FPDF_RenderPage` в принтерский HDC на драйверах A3/A4/duplex, с печатью 1–100 страниц, отменой во время нативной функции, изоляцией PDFium от фонового просмотра.
- Зафиксировать фактический формат spool/EMF и различие между векторными примитивами, драйверной растеризацией и исходными raster-изображениями. Только этот протокол позволит признать требование «векторная печать» выполненным.
- Для PDF с поворотом, штампами, рисунками, заметками экспериментальный путь должен запрещаться, сохраняя обычную растровую печать.
