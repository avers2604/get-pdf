# GD-31J.27bk — fail-closed rollback и инвентаризация остатков восстановления

Дата: 2026-11-04. Предыдущий этап: GD-31J.27bj / Draft PR #175. Изменения — отдельная stacked Draft-ветка. **Без сборки, запуска MSTest/Python unittest, стенда, Windows/Astra/SMB-испытаний, GitHub Actions или выпуска.** WORM, действующие документы, интеграцию GUP-2, нативные адаптеры и EuroOffice SaveAs не включаем.

## 1. Что реально изменено

### BK-01 — отказ от небезопасного удаления по пути в `OfficeRecoveryStore.CaptureAsync`

Ранее обработчик исключения безусловно вызывал `TryDelete(temporaryCopy)` для имени, которое получал `Func<string,Task> exportCopy`. Но экспортёр мог не создать этот объект или его могли заменить. Дополнительно удалялись `.json.tmp` и `finalCopy` по пути после промежуточной ошибки. Только факт успешно выполненного `File.Move` не доказывает, что **на момент удаления** под этим именем находится прежний OS file ID.

Теперь при ошибке или отмене *ни один* из этих путей в `CaptureAsync` не удаляется. Прежняя последовательность проверки SHA/ZIP/XML и атомарного по имени манифеста не изменена: незавершённая копия без валидного `.json` не предлагается `FindLatest` как восстанавливаемая. Если публикация манифеста успела состояться, дальнейший сбой `Prune` также не откатывает его.

**Компромисс:** после ошибки экспортера/заполнения диска/отмены появляются `.part.docx/.xlsx/.pptx`, `.json.tmp` или переименованная копия без манифеста; они остаются для расследования. Это безопаснее, чем удалять неподтверждённый объект, но требует контроля заполнения диска и нативного протокола авторизованной очистки. При больших объёмах такая политика имеет эксплуатационный риск — нельзя использовать её как финальное решение.

### BK-02 — новый `RecoveryDetachedWorkspaceInspector`

Изолированный, не включённый в рабочий UI внутренний C#-компонент, который **только перечисляет** непосредственных потомков заданного временного корня (по умолчанию `Path.GetTempPath()`) с префиксами:

- `getdoc-recovery-private-*` (private publisher);
- `getdoc-consumer-owned-*` (DeleteOnClose consumer workspace).

Условия: бюджет 1–1024 записей (по умолчанию 256), учитываются **все** встреченные элементы включая посторонние; `Truncated=true` при неполном осмотре. Никаких подкаталогов, чтения файлов, открытия дескрипторов, сортировки по предполагаемому времени смерти процесса, удаления, перемещения, записи, восстановления или запуска процессов. Выдаётся имя каталога и **непроверенный** статус: `DirectoryUnverified`, `UntrustedLinkOrNonDirectory`, `MetadataUnavailable`. Полный путь не предоставляется как «токен очистки». Неизвестные ошибки enumeration/ACL и связанные компоненты корня не превращаются в пустой успешный отчёт.

**Критично:** имя, префикс, mtime, PID, отсутствие открытого дескриптора и даже SHA не доказывают, что каталог брошен, принадлежит приложению и может быть удалён. Любая будущая очистка должна быть отдельной, явной, identity-bound операцией с подтверждением платформенной безопасности. Инвентарь этого этапа никогда не является разрешением на удаление.

### BK-03 — регрессионные спецификации (написаны, не запущены)

- Исправлены ожидаемые результаты C# MSTest для частичного экспорта, отмены, подменённой ссылки и коллизии финального манифеста: остатков может стать больше, но нет автоматической потери чужого файла, а `FindLatest` не предлагает незавершённый снимок.
- 8 синтетических MSTest в `RecoveryDetachedWorkspaceInspectorTests`: отсутствие корня, два известных префикса, обычный файл вместо каталога, бюджет на посторонних записях, путь за пределами корня, ошибка lazy enumeration, ранняя отмена, symlink (если разрешён ОС).
- Новый source-only контракт `test_recovery_orphan_inventory_contract.py`, адаптирован контракт цепочки восстановления, добавлена отдельная стадия в offline acceptance runner.

## 2. Ограничения и незакрытые P1

1. `CaptureAsync` всё ещё принимает произвольный **путь** для экспорта, а не ранее созданный, удерживаемый OS-дескриптор. Отказ от удаления устраняет одну ошибку, **не исправляя** TOCTOU в path-based publication.
2. Текущие `FindLatest` возвращают путь после закрытия проверенного дескриптора. `Discard` и `Prune` используют path-based `File.Delete` после предварительной проверки: в недоверенной среде нужен OS file-id-bound no-follow протокол.
3. `InspectIncomplete` видит `.part` и `.json.tmp`, но пока не классифицирует успешно переименованную копию `.docx/.xlsx/.pptx` **без** финального манифеста. Новый инспектор `getdoc-*private-*` не заменяет этого отдельного per-document инвентаря.
4. `Directory.CreateTempSubdirectory` не является гарантией 0700/ACL, а `FileOptions.DeleteOnClose` — доказательством поведения SMB или после падения питания.
5. Нет надёжной гарантии durability после `File.Move` без подтверждённого fsync родительской директории или протокола SMB. Нет безопасного автоматического reaper; ни один остаток не считается доказанно мёртвым.
6. При накоплении orphan-подобных артефактов требуется управление дисковым бюджетом без разрушения пользовательских данных. Любые ограничения объёма должны отказывать в **новом** создании, но не удалять старые объекты наугад.

## 3. Offline manual gates — не выполнены

| Gate | Требуемое наблюдение |
| --- | --- |
| `gd31j27bk-path-rollback-windows-ntfs-manual-e2e` | отказ/отмена до/после rename, подмена имени, отсутствие `File.Delete` в rollback, сохранность пользовательских данных |
| `gd31j27bk-orphan-inventory-astra-ext4-manual-e2e` | SIGKILL, 0700/ACL, symlink/dangling link, root symlink, bounded inventory; никаких автодействий |
| `gd31j27bk-smb-failure-no-auto-delete-manual-e2e` | сеть пропала, reopened share, частично записанный файл/манифест, не выдавать ложную восстановимую копию и не удалять |

Реальные тесты делаются исключительно на синтетических данных на отдельном офлайн-стенде, без действующих документов, WORM и пользовательских SMB-шар.

## 4. Решение о выпуске

`releaseReady=false`; все manual gates `not-run`; ветка и PR остаются **Draft**, не merge и не deploy. Нативные identity adapters Windows/Linux как ранее отключены. Условие следующего этапа — сначала проектирование и затем offline-доказательство identity-bound export/rename/delete, безопасный учёт копии без манифеста, ограничение количества новых orphan и проверка на NTFS/Astra/SMB.
