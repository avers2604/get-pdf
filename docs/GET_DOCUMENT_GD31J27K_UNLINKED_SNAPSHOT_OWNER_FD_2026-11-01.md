# GD-31J.27k — приватная безымянная копия Save As и контроль дескрипторов

**Дата:** 2026-11-01. **База:** Draft PR #123 (GD-31J.27j). **Статус:** исходники и тесты подготовлены, но ни сборка C++, ни Python/MSTest, ни реальная Qt/CEF/EuroOffice/Astra/Linux VM **не запускались**. Никакие пользовательские DOCX/XLSX/PPTX, GUP-2, SMB и WORM не затронуты.

## Причина правки

GD-31J.27j исключил подмену *имени* между проверкой и `linkat`, привязав публикацию к файловому дескриптору. Однако этот дескриптор указывал непосредственно на файл, созданный SDK. Если после публикации SDK или другой процесс продолжает писать в **тот же inode**, он изменяет уже опубликованный конечный файл. `fsync`, повторная проверка SHA и режим 0600 не дают постоянной защиты от существующего открытого пишущего дескриптора, а `fchmod` не отзывает ранее выданный доступ.

## Изменения в native_saveas_durable.h

1. При открытии каталогов требуется `st_uid == geteuid`, отсутствие group/world write. Для private scratch отдельно обязательно `mode & 0777 == 0700`, `S_ISDIR`, `nlink>=2`. Если owner/perms не подтверждены, **fail closed**.
2. После исходной проверки SDK-файла `openat(O_RDONLY|O_NOFOLLOW|O_NONBLOCK|O_CLOEXEC)`, `st_nlink==1`, SHA/metadata/`fsync` создаётся **НОВЫЙ отдельный inode** с `openat(privateDirFd, ".", O_TMPFILE|O_RDWR|O_CLOEXEC, 0600)`. Если файловая система/ядро не поддерживают O_TMPFILE, нет fallback к обычному именованному файлу или оригинальному SDK inode: **отказ**.
3. `SnapshotSyntheticBytes` читает исходный уже открытый FD в рамках 32 МиБ, пишет в anonymous inode с проверкой частичных `write`, `EINTR`, SHA-256, размера и неизменной исходной `dev/ino/size/mtime/ctime`. Никаких имён пользовательских файлов или путей из callback.
4. Безымянный файл обязан иметь `st_nlink==0` и `st_uid == geteuid`. Делается `fsync(snapshotWriter)`, затем `fchmod(snapshotWriter, 0400)` и повторный `fsync`. Отдельный read-only FD открывается через **проверенный kernel procfs** `/proc/self/fd` с `O_RDONLY|O_CLOEXEC` и проверкой равенства inode. Затем **писатель закрывается до публикации**: `snapshotWriter.closeNow()`. Писатель никогда не отдаётся CEF/SDK.
5. Публикация выполняется **только** `LinkVerifiedSourceFd(snapshotReader.value, outputDirFd, basename)`, унаследованным с GD-31J.27j: `AT_EMPTY_PATH` или проверенный procfs `AT_SYMLINK_FOLLOW`. Source SDK FD не публикуется ни при каких обстоятельствах. После появления конечного имени `nlink==1`, а исходный SDK-файл остаётся отдельным inode, и его последующие изменения **не меняют байты snapshot**, если постороннему субъекту не удалось получить доступ к самому snapshot FD/новому имени.
6. Снова проверяется SHA snapshot FD, dev/ino/size конечного имени, `fsync(outputDir)` и неизменность source. `EEXIST` — отказ без перезаписи. При любой ошибке после link конечный файл **не удаляется автоматически**; исход операции требует ручной проверки.
7. RAII `Fd` имеет `closeNow()` и запрещённые copy-конструктор/copy assignment; все snapshot FD `O_CLOEXEC`. Дескрипторы принадлежат области выполнения и закрываются при отказе. Один безымянный snapshot не имеет файлового имени до единственной точки публикации.

### Важные ограничения и честная граница доверия

Это **не** полноценная защита от произвольного непривилегированного процесса с тем же UID, если ему доступны `ptrace`, `/proc/<pid>/fd`, права `chmod` на конечный файл или уже открытый FD нового inode. Раздельное сохранение SDK source и anonymous snapshot уменьшает риск продолжения записи **именно через старый дескриптор SDK**, но не создаёт неизменяемый/WORM файл. Реальная изоляция запуска, запрет ptrace, отдельные UID/namespace/policy и проверка угроз остаются обязательными.

`fchmod(0400)` **не** защищает от прежнего открытого пишущего дескриптора и может быть изменён владельцем. Поэтому закрытие writer FD до publication обязательно, а исходные документы/сети/WORM не подключаются. Право группы/всех и поддержка O_TMPFILE тестируются только в одноразовой Linux/Wayland VM. Режим по умолчанию остаётся выключенным (CMake opt-in).

### Изменение послеаварийной семантики

В прошлой схеме финальный файл был hardlink временного SDK output; при аварии до cleanup существовал один inode с двумя ссылками. В GD31J27k final — **отдельная анонимная копия** с единственной ссылкой; временный SDK output в scratch остаётся **другим** inode. Поэтому старый `native_saveas_orphan_inventory.py` отнесёт случай существующего final с иным inode к **отвергнутым/требующим отдельной ручной сверки**; это намеренно безопаснее, чем ошибочно считать его тем же файлом. Новая трактовка состояния «опубликовано, но crash до cleanup» должна пройти полноценную VM fault-injection прежде, чем возможно вводить автоматическое восстановление. **Автоочистки по-прежнему нет**. Legacy-тесты linked nlink=2 сохраняются, поскольку могут описывать ранее созданные старые артефакты.

## Подготовленные (не выполнявшиеся) проверки

- `test_native_unlinked_snapshot_contract.py`: код создаёт O_TMPFILE без имени, требует private scratch 0700+owner, закрывает единственный writable FD до публикации, связывает только snapshot read-only FD, не использует `rename/unlink/copy` как fallback.
- `test_native_unlinked_snapshot_linux.py`: исключительно `tempfile.TemporaryDirectory` — создаёт O_TMPFILE, закрывает пишущий FD, публикует через procfd и проверяет, что поздняя запись в синтетический SDK source не влияет на final; отсутствие поддержки O_TMPFILE на Linux — **не зеленый skip**, а необходимость устранить условие стенда. Отдельная проверка закрытого дескриптора.
- Обновлены `test_native_fd_bound_link_contract.py`, `scripts/office_acceptance.py` и `scripts/tests/test_office_acceptance.py`; добавлены два pre-restore gate.
- `native_saveas_acceptance_gate.py`: **19-й** отдельный случай `same-uid-writer-after-anonymous-snapshot` и **16-й** ручной `eurooffice-gd31j27k-owner-only-unlinked-snapshot-same-uid-writer-e2e`. Строгая схема manual claims, статус `releaseReady=false` и запрет production Save As сохраняются.

## Дальнейший блокер перед нормальным Save As

Необходимо отдельно проверить **реальный owner/UID/namespace sandbox**, отсутствие доступа других приложений к `/proc/self/fd`, работу O_TMPFILE на конкретной версии Astra Linux, доступность `AT_EMPTY_PATH/procfs`, аварийные точки `fsync` и гонки времени жизни дескрипторов EuroOffice SDK. Без SDK/CEF сборки и VM fault-injection нельзя утверждать работоспособность и окончательную безопасность. Проект продолжает использовать существующую лабораторную архитектуру; пользовательские файлы не включать.
