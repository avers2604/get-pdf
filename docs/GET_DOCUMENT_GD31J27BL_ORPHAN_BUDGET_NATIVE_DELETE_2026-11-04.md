# GD-31J.27bl — учёт копий без манифеста, лимит новых снимков и подготовка нативного удаления

**Дата:** 2026-11-04. **Основание:** GD-31J.27bk, черновик PR #176. Работа находится в отдельной stacked Draft-ветке без публикации в `main`.

## Статус и границы

Внесены изменения в исходники и написаны синтетические регрессионные сценарии. **Сборка .NET, MSTest, Python unittest, GitHub Actions, NTFS/Astra/SMB, реальное аварийное завершение и стендовые испытания не выполнялись.** `releaseReady=false`, ручные проверки — `not-run`.

Это не переход в production. Действующие пользовательские документы, WORM-оригиналы, GUP-2, нативный EuroOffice SaveAs и нативные дескрипторные адаптеры не включены.

## BL-01 — финальные OOXML-копии без замеченного манифеста

`OfficeRecoveryStore.InspectIncomplete` теперь различает три вида наблюдаемых артефактов (для одного исходного документа):

| Вид | Имя | Значение |
| --- | --- | --- |
| `StagedOfficeCopy` | `GUID.part.docx/.xlsx/.pptx` | незавершённый экспорт |
| `TemporaryManifest` | `GUID.json.tmp` | ещё не опубликованный commit-marker |
| `FinalCopyWithoutObservedManifest` | `GUID.docx/.xlsx/.pptx` | переименованная копия, к которой **не увидели** `GUID.json` |

Последняя категория **не означает доказанное отсутствие манифеста**, не доказывает, что создавший её процесс завершился, и не предоставляет разрешения на восстановление либо очистку.

Выполняется один ограниченный обход имён (1–1024 записи, включая чужие объекты); до классификации финальной копии строится наблюдённый набор имён. Если обход прерван бюджетом (`Truncated=true`), **финальные копии не объявляются безманифестными**: отсутствие `GUID.json` из неполного списка недоказуемо. Если имя манифеста наблюдается, финальная копия не включается в эту категорию **независимо от формата/содержимого манифеста**. Никакой JSON, ZIP, документ, файл или дескриптор в инспекторе не открывается, не изменяется и не удаляется; подозрительные ссылки классифицируются как недоверенные.

Конкурентное появление `GUID.json` *после* завершения перечисления по-прежнему возможно. Инвентарь — моментальное диагностическое наблюдение, а не линейризуемый протокол принятия решения или deletion token.

## BL-02 — консервативный admission control новых снимков

Создан `RecoveryCaptureAdmission.EnsureMayCapture(OfficeRecoveryIncompleteInventory)`. Перед созданием каталога и перед вызовом экспортёра `OfficeRecoveryStore.CaptureAsync` запускает `InspectIncomplete` с бюджетом 1024.

Новый экспорт блокируется (исключением `IOException`, без записи/удаления файлов), когда:

- обследование не закончено — `Truncated=true`;
- наблюдено **16 или больше** незавершённых кандидатов (каждый .part, .json.tmp или финальная копия без замеченного манифеста), включая ссылки и кандидатов с недоступными метаданными.

При менее чем 16 наблюдаемых артефактах существующая последовательность capture остаётся без изменений: экспорт → SHA/ZIP/XML проверка → rename копии → `CreateNew` манифеста → rename манифеста. Поведение этапа bk — не удалять пути при rollback — сохраняется.

**Ограничения:** это ограничение количества кандидатов для **одного исходного документа**, а не общий байтовый лимит свободного места. 16 объектов могут быть значительно больше доступной ёмкости диска; отсутствует межпроцессная/SMB-блокировка и глобальный контроль всех документов. Два процесса могут пройти проверку одновременно. До production нужны доступное место на томе, атомарные reservation/lease, дедупликация и лимит общего бюджета с безопасной стратегией отказа **без** стирания чужих файлов.

## BL-03 — подготовка identity-bound удаления, но НЕ само удаление

Создан `RecoveryNativeDeletionPreparation.cs`:

- `RecoveryNativeDeleteKey` принимает только 64 ASCII hex для исходного hash-каталога и `GUID` + точное разрешённое расширение `.docx/.xlsx/.pptx/.part.*.json/.json.tmp`; пути, `..`, посторонние имена не принимаются.
- `RecoveryNativeDeleteEvidence` содержит утверждения об OS handle identity — идентификаторы каталога и файла при открытии и повторной проверке, корректность relative/no-follow и подтверждение изоляции записи в каталог.
- `RecoveryNativeDeletionPreparationGate.InspectForPlanning` отклоняет неполные идентификаторы, перемену file-id, несовпадение parent/device/platform и отсутствие необходимых признаков.
- Реальные `WindowsRecoveryNativeDeleteObservationAdapter` и `LinuxRecoveryNativeDeleteObservationAdapter` имеют `SupportsHandleBoundDeleteObservation=false` и отказывают в вызове. Метод только оценивает структурную согласованность **заявленных** данных; даже успешная имитация не доказывает, что запись действительно принадлежит приложению. **Никакой delete API не предоставлен.**

Не следует путать Windows delete-by-handle с POSIX `unlinkat`: в Linux удаление по относительному имени само по себе не связывает атомарно результат с inode, проверенным ранее по дескриптору. До включения нужен защищённый доверенный каталог с исключением конкурентного переименования, корректный no-follow протокол, OS-level проверки и испытания на NTFS, Astra/ext4 и SMB.

## BL-04 — подготовленные, НЕ запущенные тесты

- 4 новых MSTest в `OfficeRecoveryIncompleteInventoryTests`: финальная копия без манифеста; копия с повреждённым, но наблюдаемым манифестом; неполный обход; неизвестное имя/формат.
- 4 MSTest в `OfficeRecoveryCaptureAdmissionTests`: порог 16, неполный обход, допустимый диапазон и ранний отказ перед экспортом с сохранением всех файлов.
- 6 MSTest в `RecoveryNativeDeletionPreparationTests`: грамматика имён, запрет реальных адаптеров, смена identity, отсутствие изоляции, mismatch платформы и положительный **искусственный** структурный пример, который ничего не удаляет.
- Добавлен Python **source-only** контракт `test_recovery_orphan_budget_native_delete_contract.py`. Обновлены предыдущий контракт инвентаризации и stacked chain checker; runner регистрирует их до восстановления зависимостей.
- Зарегистрированы четыре ручных gate, все `not-run`: Windows NTFS orphan; Astra/ext4 admission; SMB concurrent admission; отказ в native identity deletion. Никакие проверки в данном этапе не запускались.

## P1 до допуска к производству

1. Реальный OS-handle-bound экспорт, commit и delete без path-TOCTOU; для Linux — защищённая модель directory writer isolation.
2. Отсутствие общесистемного и межпроцессного контроля дискового пространства, отсутствует предотвращение одновременных start двух exporters.
3. Недоказанная устойчивость `DeleteOnClose`, rename/fsync и SMB-потери соединения после аварии.
4. `FindLatest` возвращает путь после закрытия проверенного дескриптора; `Discard/Prune` остаются path-based.
5. Синтетические тесты и проверки NTFS/Astra/SMB ещё не запускались.

**Решение:** сохранить Draft; `main` и production не трогать; `releaseReady=false`; автоматическое удаление останков и WORM-публикацию не включать.
