# GD-31J.27br — учёт блокирующих проверок перед выпуском «ГЭТ Документ»

Дата: 2026-11-05. База: GD-31J.27bq / Draft PR #182. **Только отдельная Draft-ветка.** Никаких изменений production `OfficeRecoveryStore`, публикации/удаления файлов, `main`, GitHub Actions, настоящих документов или сертификатов допуска.

## Причина

В `scripts/office_acceptance.py` после этапа BQ зарегистрировано **135 ручных gates**: 82 по цепочке аварийного восстановления (`gd31j`), 44 по EuroOffice/Native SaveAs (`eurooffice-`) и 9 общих. Отсутствие результатов нельзя показывать как «выполнено». Технические Draft PR по 27ao–27bq **не являются** E2E-аттестацией. Каждый новый отчёт `office_acceptance.py` инициализирует ручные gates как `not-run`.

## Выполнено в BR

- `scripts/recovery_release_readiness.py`: **read-only CLI**. Статически извлекает обязательные `MANUAL_GATES` из AST (буквальный tuple) без исполнения файла, без загрузки документов или сети. Группирует незакрытые проверки.
- Без входного отчёта все gates классифицируются `no-evidence`, а не `passed`. С существующим JSON принимается **только** `schemaVersion=1`, Windows/Linux и точный Git SHA, явно заданный оператором.
- Отчёты c неподходящей ревизией, отсутствующим обязательным gate, неизвестным статусом, дубликатами каталога и ошибками схемы **не дают ложного разрешения**. Значение `passed` в JSON трактуется строго как `claimed-passed-unverified` до отдельной доказательной приёмки.
- Анализатор **всегда** возвращает `releaseReady=false`, `status=blocked`. Код выхода 0 говорит лишь об успешной генерации инвентаризации; это **не статус допуска**.
- Чтение JSON ограничено 1 MiB; символические ссылки как входной отчёт отвергаются. Отчёт не редактируется и не перезаписывается.
- Добавлено **8 Python unittest** и регистрация `recovery-release-readiness-tests` перед offline NuGet restore в обычном `office_acceptance.py`.

## Команды для автономного ПК (без стенда)

Показать текущий перечень незакрытых проверок, не выполняя никаких испытаний:

```sh
python3 scripts/recovery_release_readiness.py --details
python3 -m unittest discover -s scripts/tests -p test_recovery_release_readiness.py -v
```

Разобрать уже созданный локальный отчёт, **для того же коммита**, с явно проверенной ревизией:

```sh
python3 scripts/recovery_release_readiness.py \
  --report artifacts/local-acceptance/EXISTING_REPORT.json \
  --expected-revision REPLACE_WITH_EXACT_40_HEX_GIT_SHA \
  --details
```

На Windows можно использовать `py -3` вместо `python3`. Нельзя подменять существующие протоколы, подставлять случайные SHA или воспринимать JSON как сертификат успешных испытаний.

## Правила завершения

1. Разрешённый для испытаний коммит фиксируется по SHA; собранный из offline NuGet feed бинарник, лог и протокол относятся только к этому SHA и к конкретной ОС.
2. Выполняются локальные Python contract/unit tests, потом `.NET 10` build/MSTest; исходные проверки не заменяют реальную компиляцию.
3. На физическом или согласованном изолированном стенде выполняются **независимые** Windows, Astra и SMB проверки с негативными сценариями (без пользовательских документов).
4. По каждому обязательному gate прикладываются минимальные подтверждения: платформа, билд/хеш, тест, ожидаемый/фактический исход, ответственное лицо и дата. Недоступность теста — `not-run`, а не «условно принято».
5. Только после отдельного security review можно обсуждать разрешение native write/delete capability, merge цепочки Draft PR в правильном порядке, SSO/GUP-2/WORM, миграции Linux coordinator 0755→0700 и production release. Этот BR **ничего не утверждает автоматически**.

## Честный статус проверки BR

В изолированном Python-контуре было выполнено **8/8 синтетических unittest** для нового анализатора, но реальный runner всего репозитория, `.NET` сборка, MSTest, Azure/GitHub Actions, системные вызовы Windows/Astra, печать и SMB **не запускались**. Ручные gates по-прежнему не подтверждены. Наличие PR не изменяет `releaseReady=false`.
