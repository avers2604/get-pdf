# GD-31J.27 — корреляция native EuroOffice SaveAs + независимого OOXML/canary

**31.10.2026 · база GD-31J.26 / Draft PR #112 · подготовлены исходники и тесты. Сборка, тестовые процессы, CEF и реальные сохранения не запускались.**

## Назначение и границы доверия

У предшествующих этапов разные источники данных:

- **GD-31J.26**: CEF SDK выдаёт одну диагностику `getdoc-native-saveas-candidate-lab/1` с `sessionId/tabId/fixtureName`, фактом запроса `CEF_LOCALFILE_SAVE`, ответом через `Apply(CEF_LOCALFILE_SAVE_PATH)`, `OnSave`, состоянием отмены, неизменностью исходного файла, опубликованным SHA-256. Все данные здесь — **самоотчёт процесса**, а не подписанная аттестация. `nativeSaveProven=false` даже при наличии файла.
- **GD-31J.25**: отдельный read-only `synthetic_roundtrip.verify()` повторно открывает реальный ZIP, валидирует манифест и SHA исходного fixture, CRC частей, OOXML content types/relationships, контролирует внедрение **ровно одной** синтетической метки в `w:t/s:t/a:t` и SHA результата. Он ничего не знает о том, какой процесс сохранил документ.

**GD-31J.27** объединяет эти сведения **только в лабораторный коррелированный кандидат**, не разрешая работу с реальными документами. Соответствие двух квитанций **не доказывает происхождение выходного файла**: пользователь или вредоносный процесс способен подделать native JSON, если контролирует стенд. Допуск native OS-sandbox/происхождения исполняемого файла — отдельная обязательная проверка.

## Реализация

1. Новый `probes/eurooffice-desktop/cef_lab/native_ooxml_join.py` — **строго читающий** Python-процесс. Получает ровно **одну** ASCII JSON строку из stdin (максимум 2048 байт, завершающий LF; лишние строки/байты отклоняются), четыре аргумента `--staging`, `--fixture`, `--session`, `--tab`. Никаких команд shell, запуска внешних процессов, записи файлов или сетевых запросов.
2. Native JSON проверяется по **18 точным полям**, с отказом от повторов ключей, неверных типов, чужих/нулевых GUID32, дополнительного содержимого и несоответствующих сеанса, вкладки или fixture. Для продолжения необходимы `nativeSaveRequestObserved=true`, `savePathProvided=true`, `nativeOnSaveAfterAnswer=true`, `saveCancelledAfterAnswer=false`, `sourceUnchanged=true`, `publishedToDisposableOutput=true`. Все заявленные production/verified-флаги должны быть `false`.
3. Затем `synthetic_roundtrip.verify(staging, fixture)` **заново** читает реальные файлы из зафиксированных каталогов GD-31J.6/25: проверка manifest/исходного SHA, zip, CRC, разрешённых OOXML-частей, обязательного расположения canary и самостоятельного выходного SHA-256.
4. `outputSha256` реального файла **должен буквально совпасть** с хешем нативной квитанции, а source SHA и выходной файл не могут совпадать. Оригинал и опубликованный результат повторно считываются для заключительной сверки SHA (это защита от обычных гонок, а **не** от полномочного противника в той же VM).
5. Только при полном совпадении выдаётся ровно один ограниченный JSON `getdoc-native-ooxml-joined-candidate-lab/1`. В нём session/tab/fixture/source SHA/output SHA, `nativeEventChainSelfReported=true`, `independentPackageVerified=true`, `syntheticCanaryVerified=true`, `outputDigestCorrelated=true`, `sourceUnchanged=true`. Пути, текст документа, данные пользователя, ключи и содержание XML в квитанцию не попадают.
6. `EuroOfficeNativeOoxmlJoinCandidate.Parse` — строгий C# парсер этого объединённого JSON: только три fixture, точная схема и набор полей, контроль типов/дубликатов, ID, SHA-256, запрет привилегий. Флаги `nativeSaveProven`, `documentVerified`, `saveVerified`, `approvedForProduction` навсегда `false`.
7. Добавлены Python позитивные/негативные unit-тесты для DOCX/XLSX/PPTX, подделки событий, wrong hash, forged JSON, двойных строк, недопустимых источников, повреждения файла, отсутствия canary; Python static source contract; MSTest C#; тест offline runner для планирования. **Все сценарии только подготовлены и включены в будущий локальный runner; запуск отложен.**

## Будущий ручной E2E в отключённой от корпоративного контура VM

1. Положить в отдельную disposable offline VM закреплённый исходный SDK и точные бинарники GD-31J.24/26, проверить все SHA и AGPLv3+допусловия, запретить доступ к SMB/GUP-2/WORM, внешней сети и пользовательским документам.
2. Подготовить три synthetic GD31J6 fixtures+manifest, отдельный размеченный каталог `gd31j25-output/`. Убедиться, что в нём нет целевого файла. Запустить нативный `--open-staged-native-saveas-lab` с настоящими GUID32; **ручной** Save As с единственной синтетической меткой, исходник остаётся неизменен.
3. Передать **единственную строку stdout native host** в stdin `native_ooxml_join.py`. При использовании pipeline оператор должен контролировать код возврата нативной программы (например, с `set -o pipefail`), потому что успешная проверка самозаявленного JSON без установленного процесса недостаточна.
4. Пример синтаксиса *для последующей лаборатории*, **не запускать на корпоративной рабочей станции**:

   ```sh
   python3 probes/eurooffice-desktop/cef_lab/native_ooxml_join.py \
     --staging /ABSOLUTE/APPROVED/DISPOSABLE/STAGING \
     --fixture gd31j6_writer.docx \
     --session 102030405060708090a0b0c0d0e0f010 \
     --tab f010e0d0c0b0a0908070605040302010 \
     < /ABSOLUTE/APPROVED/ONE-LINE-NATIVE-STDOUT-RECEIPT.jsonl
   ```

   Указанный файл stdout должен содержать **одну целую строку** с завершающим LF из отдельного GD-31J.26 сеанса. Чтобы не перезаписать старую квитанцию, запись/хранение stdout организуются **вне** этого readonly проверяющего компонента, строго по отдельной политике одноразового лабораторного evidence. `native_ooxml_join.py` не создаёт и не читает такой файл напрямую.
5. Повторить для Calc/Impress. Открыть каждый полученный документ другим редактором; проверить текст/ячейку/слайд, актуальность и целостность, сравнить ожидаемое форматирование.
6. Отрицательные E2E: заранее созданный output; CEF OnSave без изменения/без SavePath; отмена; повтор Save As; чужой tab/session; изменение manifest; искажение одного байта ZIP; перенос canary в метаданные; подмена файла после native callback; неправильный SHA; попытка включить режим без PIN SDK/прошлого overlay; сбой native runtime; повреждённые JSONL.

## Что не заявляем готовым

Совпадение `source/output SHA` и одной контрольной метки **не подтверждает подлинность редактора**, полную совместимость Microsoft Office или безопасность совместного редактирования. Привязка к происхождению/подписи native процесса, файлоизолирующая VM, реальный нативный save/restore, проверка полноты OOXML и 2–5–10 пользователей должны пройти отдельную лабораторию и юридический аудит. Ни производственный лаунчер, ни ГЭТ Проводник, ни GUP-2, ни WORM/SMB, ни печать здесь не менялись. LibreOffice/UNO fallback не затронут. **Не сливать в `main`, не включать GitHub Actions и не выполнять на настоящих документах.**
