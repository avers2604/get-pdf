# GD-31J.20 — безопасное локальное сохранение документов (LibreOffice/UNO fallback)

**Дата:** 29.10.2026. **База:** GD-31J.19 Draft PR #89. **Статус:** исходный код и MSTest/acceptance тесты подготовлены, сборка и выполнение тестов **отложены**, `main` не менялся. EuroOffice CEF OSR остаётся изолированным лабораторным экспериментом.

## Задача

Пока полноценное встраивание EuroOffice DesktopEditors в ГЭТ не подтверждено, существующая Windows-вкладка редактора использует локальный LibreOffice/UNO. До GD-31J.20 `EditorDocument.SaveAsync()` напрямую вызывал UNO `store()`, даже если исходный DOCX/XLSX/PPTX изменился другим приложением после открытия; `storeToURL()` мог перезаписать существующий файл, выбранный в диалоге копирования. Новое поведение снижает эти риски, **не выдавая fallback за нативный EuroOffice**.

## Реализованные изменения

### 1. Guard для исходного документа

- `OfficeFileRevisionGuard.CreateAsync` создаёт снимок пути, размера, UTC времени изменения и полного SHA-256. Проверка ограничена 256 МиБ, чтение использует bounded buffer и стандартные локальные файловые API; внешняя сеть приложением не создаётся (UNC/SMB использует ОС).
- При `LibreOfficeEditor.OpenAsync` снимок берётся **перед** UNO load, а **после** открытия проверяется повторно. Если файл заменён/изменён во время загрузки, приложение закрывает открытый нативный документ и отказывает в ненадёжной сессии.
- `OfficeRevisionSaveCoordinator` сериализует вызов `EditorDocument.SaveAsync`: перед UNO `store()` выполняется повторная сверка SHA/размера/времени. Конфликт или отсутствие оригинала ⇒ `OfficeFileConflictException`, UNO save **не вызывается**, исходный файл не перезаписывается данным вызовом.
- Версия принимается заново **только после** успешного ответа UNO и чтения нового снимка. При неудачной записи или проверке старый baseline остаётся и дальнейшее автоматическое сохранение не разрешается. Несохранённый документ остаётся доступен для `Сохранить копию…`.
- При конфликте `OfficeEditorPane` выводит видимое предупреждение с кнопкой сохранения новой копии. Аварийные копии `OfficeRecoveryStore` на отказанном сохранении не удаляются.

### 2. Публикация копий без перезаписи

- `OfficeCopyPublisher.PublishAsync` вызывает существующий UNO `storeToURL()` / PDF export на уникальное `.getdoc-copy-<GUID>.<ext>` в каталоге назначения.
- После успешной записи проверяет ненулевой размер файла и публикует `File.Move(..., overwrite:false)`. Неполная или неуспешная операция не должна создать видимый файл под именем назначения. Старые файлы не перезаписываются, даже если появились в ходе экспорта.
- При исключении временный файл удаляется по возможности. После аварийного выключения без `finally` временные файлы могут остаться — необходима **отдельная** безопасная очистка только подтверждённых staging-файлов, не затрагивающая пользовательские документы.
- Кнопки `Сохранить копию` и `Сохранить как PDF` в редакторе используют эту публикацию. PDF из печатного мастера получает уникальное имя как прежде.
- Это новый консервативный контракт: существующий файл даже при выборе в диалоге больше не перезаписывается. Нужно сохранить новую копию под свободным именем.

## Тесты подготовлены, но НЕ выполнены

- `OfficeFileRevisionGuardTests`: отсутствие внешнего изменения; изменения при **том же размере и восстановленной временной метке**; атомарная замена, удаление исходника; смена baseline только после удачного store; запрет вызова native save после конфликта; неуспешный store не выдаётся за успешный.
- `OfficeCopyPublisherTests`: запись в destination folder, запрет перезаписи, отказ при оборванном экспорте и пустом выходе, удаление staging в обычном сценарии ошибки.
- `scripts/office_acceptance.py`: добавлен manual release gate `office-native-save-conflict-and-no-overwrite-copy`, закреплённый тестом runner. Базовые `GetDocument.Office.Tests` запускаются локально после утверждения лаборатории.
- Реальный сценарий: ПК А открывает DOCX/XLSX/PPTX; ПК Б изменяет SMB-файл; ПК А нажимает Ctrl+S и получает **отказ без перезаписи**, сохраняет копию, затем сравнивает обе версии. Дополнительно выполнить проверку 2/5/10 пользователей, переход в offline, Win 10/11, DPI и слабые ПК.

## Существенные ограничения

**Это optimistic check, а НЕ атомарный CAS.** Между сверкой файла в .NET и UNO `store()` остаётся окно гонки. Даже полный SHA не гарантирует отсутствие внешней записи после проверки. Для корпоративных хранилищ и WORM необходимо использовать отдельный серверный CAS/version sink или проверенный механизм эксклюзивного сохранения. До этого нельзя утверждать, что сетевое конкурентное сохранение полностью безопасно.

Проверка ненулевой длины staging-файла **не подтверждает** форматную корректность DOCX/XLSX/PPTX, обратную совместимость с Microsoft Office или валидность PDF. Это остаётся отдельным release gate (OOXML ZIP/OPC, открытие в Office, визуальные и структурные diff). Windows HWND-встраивание LibreOffice — ранее существующий fallback, не обещание проверенной кроссплатформенной интеграции EuroOffice. Никаких изменений в CEF, Nextcloud, GUP-2, корпоративном CAS/WORM, SSO или серверных разрешениях на запись этим PR нет.

**Следующая задача GD-31J.21:** сократить гонку между .NET preflight и native UNO `store()` через ограниченную проверку исходного файла непосредственно внутри офлайн-моста и подтверждённую write receipt; после этого — полный E2E, но даже такой bridge не заменяет серверный CAS.
