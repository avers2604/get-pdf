## Находки GD-23 и исправления

### 1. Принудительно односторонняя печать в IPP

`CupsDeviceCapabilities.Supports` до GD-23 не учитывал явно предоставленный `sides` при `PrintDuplex.OneSided` и мог считать допустимым принтер, который вообще не объявляет `one-sided`. Теперь, если список `sides` присутствует, односторонний режим должен быть в нём явно указан. Если `sides` отсутствует, сохранён обратносуместимый fallback для базового A4/simplex. Добавлены регрессионные тесты обоих случаев.

### 2. Неограниченные stdout/stderr процессов печати

`LocalPrintBroker.RunAsync` прежде применял `ReadToEndAsync` сразу к stdout и stderr `lp` / `lpoptions` / `lpstat` и Windows PrintWorker. Ошибочный или вредоносный драйвер мог прислать гигабайты stderr — объём информации ограничивался только памятью компьютера.

В GD-23 добавлен `BoundedProcessOutput`: stdout буферизуется максимум до **65 536 символов**, stderr максимум до **8192 символов**. Оба потока продолжают вычитываться до EOF, поэтому процесс не блокируется на заполненной трубе. Если stdout превысил лимит, результат отвергается. Сами сообщения драйвера/пути из stderr пользователю не показываются.

Новые тесты: короткая строка, ровно лимит, 512 КиБ лишних данных, отмена; интеграционный fake-CUPS выводит более 100 КиБ для проверки реального `LocalPrintBroker`.

### 3. Офлайн-восстановление NuGet

Базовые скрипты GD-22 выполняли `dotnet restore GetDocument.slnx` без ограничения источников пакетов. В изолированной сети это могло зависнуть на публичных NuGet-серверах. Вместо замены общего workflow добавлены **строгие самостоятельные офлайн-сценарии**:

```bash
bash scripts/verify-get-document-offline-linux.sh /srv/get/nuget-feed
```

```powershell
pwsh -File scripts/verify-get-document-offline-windows.ps1 -OfflineNuGetFeed 'D:\GET\NuGetOffline'
```

Оба требуют локальный каталог пакетов и `.NET 10 SDK`, вызывают `dotnet restore ... --source <локальный каталог> -p:NuGetAudit=false`, а для дальнейших сборки и тестов используют `--no-restore`. Linux включает набор CUPS-интеграционных тестов, Windows отдельно собирает `GetDocument.PrintWindows.csproj`.

Опция `NuGetAudit=false` необходима только потому, что закрытый контур не имеет публичного vulnerability feed. Она **не отменяет обязанности заранее проверить и закрепить перечень версий пакетов** на административном стенде, сверить SHA-256/подписи поставки, лицензии и базы уязвимостей до доставки пакетов в контур. Офлайн-скрипты не скачивают `.nupkg` и не требуют Интернет.

## Остающиеся ограничения

- **Нет подтверждённой компиляции и MSTest GD-17…GD-23** в доступной среде: `.NET SDK` отсутствует, интернет-доступ GitHub из командной строки тоже недоступен. Наличие Draft PR, отсутствие merge conflicts и изучение документации Microsoft **не заменяют** локальную сборку.
- Нельзя гарантировать корректность драйверных `PrintTicket.PagesPerSheet`, `InputBin`, совместного режима A3 + лоток/дуплекс и фактических полей печати без тестирования конкретных МФУ.
- Тестовый fake-CUPS подтверждает только семантику аргументов и интерфейс локальной очереди. Он **не печатает бумагу**, не подтверждает реальную работоспособность CUPS на Astra Linux и не заменяет стенд с безопасной сетевой очередью.
- Квитанция `request id is PRINTER-42` и Windows `submitted` подтверждают только постановку в очередь, но **не физическую печать**.
- Тесты Office с несохранёнными изменениями требуют Windows + корректный встроенный LibreOffice с Python UNO. На других системах тесты помечаются `Inconclusive`.
- Режим `number-up=2/4` с произвольным подмножеством исходных страниц пока сознательно отключён в CUPS из-за различий в нумерации выходных страниц.

## Порядок локальной приёмки

1. На административном компьютере сформировать **одобренный офлайн NuGet feed** и зафиксировать версии, лицензии и SHA-256 пакетов; отдельно подготовить .NET 10 SDK, PDFium и LibreOffice/UNO без сетевых загрузок.
2. На Windows и Astra Linux запустить **строгие** офлайн-скрипты GD-23, собрать и выполнить весь локальный MSTest. Обязательно фиксировать количество тестов `Passed/Failed/Skipped/Inconclusive`, так как формальный ExitCode 0 может скрывать `Inconclusive` Office.
3. Проверить CUPS имитаторы: GET_SIMULATOR, недопустимые лотки, colour/A3/duplex, недоступный spool, превышение stdout, SHA-256 и контроль job ID.
4. Прогнать Office DOCX/XLSX/PPTX с несохранёнными правками → PDF snapshot → мастер ГЭТ, удостовериться, что WORM не изменён, исходный документ не сохранён принудительно.
5. На тестовых физических HP/Canon/Булат/Катюша, если доступны, выполнить 1/2/4-up, диапазоны, A4/A3, цвет/mono, лотки/дуплекс и сравнить тираж с предварительной оценкой. Проверить ошибку неизвестной очереди и реальную отмену.
6. Только после зелёных локальных сборок, тестов и актов приёмки привести stacked PR к одной последовательно сливаемой цепочке и рассмотреть финальный релиз. Не включать GitHub Actions по умолчанию.
