# GD-30 — проверка SHA-256 PDF непосредственно перед CUPS spool

**Дата:** 27 октября 2026. **База:** GD-29 / PR №56. **Статус:** Draft, работа без выполнения реальной сборки по текущему решению.

## Найденный дефект

До GD-30 `LocalPrintBroker.SubmitPdfAsync` делал SHA-256 проверку подготовленной копии PDF, затем асинхронно вызывал `lpstat -e`, а при выбранных лотке/цвете/A3/дуплексе — `lpoptions -p QUEUE -l`. Потом без повторной сверки вызывал `lp ... <path>`. На Linux CLI `lp` самостоятельно открывает документ по переданному пути. Если частный снимок был изменён между первым хэшированием и вызовом `lp`, происходило нарушение обещания печатать **тот же PDF**, который просмотрел оператор.

Такое изменение маловероятно при обычной работе в каталоге пользователя с разрешениями `0700/0600`, но в закрытой корпоративной системе обработку целостности нельзя строить исключительно на вероятности. Сценарий воспроизводим через POSIX-симулятор, без принтера.

## Исправление

- SHA-256 извлечён в `LocalPrintBroker.VerifyPrintableDigestAsync`, используется и при первичной проверке, и **ещё раз прямо после обнаружения очереди/возможностей устройства, непосредственно до `CupsPrintArguments.Create` и запуска `lp`**.
- Проверяется размер по `PrintFileSnapshot.MaxBytes` и полное значение SHA-256 через `CryptographicOperations.FixedTimeEquals`.
- В случае расхождения вызывается `InvalidDataException`, а `lp` не запускается: задание ещё **не принято**; мастер выводит существующее сообщение об ошибке целостности.
- Windows PrintWorker уже повторно сверяет SHA-256 у себя после запуска, до `XpsDocumentWriter.Write`, поэтому Windows-ветка и контракт не изменялись.
- Создание, просмотр, удаление и WORM-оригиналы не меняются.

## Новые регрессионные проверки

1. `ChangedSnapshotDuringPrinterDiscoveryIsRejectedEvenWithoutOptionsProbe` — `lpstat -e` изменяет тестовую PDF-копию, обычный A4/simplex не вызывает `lpoptions`, итог: `InvalidDataException`, `lp` не запускался.
2. `ChangedSnapshotDuringCupsCapabilityProbeIsRejectedBeforeLp` — `lpoptions` изменяет PDF при запросе цветного режима уже **после** первой проверки SHA-256, итог такой же.
3. Фиктивные `lpstat/lpoptions` продолжают выполняться **только** в тестовом `PATH`; настоящую очередь CUPS и реальные принтеры эти тесты не вызывают.
4. Оба сценария добавлены в обязательные `ReleaseReportEvaluator.RequiredTests("Printing", "linux")`; ReleaseGate-self-test требует наличие их названий, а GD-29 `--audit-contracts` проверяет наличие реальных атрибутированных методов до MSTest.

## Ограничения модели защиты

Повторное хэширование закрывает обнаруженный интервал между первой проверкой и **началом** запуска `lp`, но **не устраняет полностью TOCTOU**: файл потенциально может быть изменён между второй проверкой и чтением его процессом `lp`. Полная байтовая неизменяемость требует безопасной подачи уже зафиксированных данных в spool (например, через ограниченный поток с проверкой происхождения байтов или другой поддержанный CUPS workflow). Этот вариант необходимо отдельно проектировать и проверять с учётом слабых ПК, лимита PDF 128 МиБ и невозможности держать все документы в ОЗУ.

Ключевое разграничение: полученный от `lp` идентификатор подтверждает **принятие в очередь**, не завершение физической печати. При неопределённом результате автоматический повтор запрещён.

## Что сделано и что не заявляется

Исходный код изменён в GitHub, подготовлены два Linux MSTest для существующего fake-CUPS и дополнены обязательные TRX-правила. Эти тесты **не выполнялись**: пользователь попросил продолжать разработку **без реальной сборки**, в среде нет .NET 10 SDK/доступа к МФУ. Статический просмотр исходников не заменяет испытания.

Когда будет разрешена сборка, обязательные команды:

```bash
bash scripts/verify-get-document-release-linux.sh /srv/get/nuget-feed
```

```powershell
pwsh -File scripts/verify-get-document-release-windows.ps1 -OfflineNuGetFeed 'D:\GET\NuGetOffline'
```

Ни `main`, ни Euro-Office PR №42/#52, ни WORM-оригиналы не изменяются; никаких GitHub Actions.
