# GD-31J.29 — синтетическая reviewed-копия после проверки Save As

**Дата:** 29.10.2026. **База:** Draft PR #100 (GD-31J.28). **Статус:** код, unit- и source-contract-тесты подготовлены, но **никакая сборка, тесты или CEF/Qt VM не запускались** согласно ранее утверждённому порядку. Это НЕ production-сохранение, НЕ WORM-операция и НЕ функциональность пользовательского лаунчера.

## Почему нужен новый блок

После появления полноценной нативной диагностической квитанции v2 у нас есть проверенный по структуре OOXML-кандидат в закрытом synthetic staging. Однако нельзя выдавать пользователям произвольные локальные пути, переименовывать WORM-оригиналы, создавать неполный опубликованный файл или автоматически перезаписывать уже существующую редакцию. `File.Move(..., overwrite:false)` не является достаточной универсальной гарантией crash-safe атомарности, поскольку перемещение через границы томов способно преобразовываться в копирование. Более того, сброс данных файла и синхронизация каталога/барьеров накопителя — разные проверки.

## Реализация `EuroOfficeSyntheticReviewedSnapshot`

Метод `Commit(stagingRoot, review, labApproved=false)` **недоступен при отсутствии явного разрешения**, и нигде не вызывается обычным GET launcher, GUP-2/Nextcloud или WORM. Перед записью он требует:

1. `EuroOfficeNativeSaveAsLab.Review` с реально выданным структурно проверенным OOXML-кандидатом, связанным с `EuroOfficeNativeSaveAsEventReceipt` v2 и `failureCode == candidate_untrusted`, `phase == quarantined`, `CorrelatedNativeCallbacks`, состоянием `SavedCandidateValidatedButUntrusted`. Поддельный `SaveCompleted=true` не поддерживается.
2. Только разрешённые синтетические имена `gd31j6_writer.docx`, `gd31j6_calc.xlsx`, `gd31j6_impress.pptx`; только исходный формат. Карантинный файл строго `gd31j26-saveas-candidate-<session32>.<ext>`; проверяются имя, сеанс, путь, SHA-256 и размер.
3. Существующий манифест `gd31j6-fixture-manifest.json`, точно `schema=gd31j6-office-fixtures/1`, `purpose=test-only-local-ooxml-no-corporate-documents`, ровно 3 записи и соответствие эталона по размеру и SHA-256; он **не является цифровой подписью**. Исходный эталон снова хешируется непосредственно перед фиксацией.
4. Абсолютный локальный root, запрет Windows UNC/SMB, отсутствие reparse points/symlinks на всех проверяемых компонентах пути, **уже существующий каталог** `reviewed` без автоматического создания. Новое имя: `<staging>/reviewed/gd31j29-reviewed-<session32>.<ext>`. Существующий результат или каталог с этим именем — отказ, без удаления и перезаписи.

### Двухфазная последовательность

- После повторной `EuroOfficeNativeArtifactCandidate.InspectRevision` создаётся новый случайный `reviewed/.gd31j29-pending-<random32>.tmp` с `FileMode.CreateNew`, `FileShare.None`, `FileOptions.WriteThrough`. Копируются **только** байты прошедшего проверку карантинного кандидата, ограничение 128 МиБ. Выполняется `Flush(true)`.
- После закрытия дескрипторов повторно проверяются размер/SHA-256 pending, исходный эталон и сам карантинный файл. Любое изменение означает отказ.
- После проверки конфликтов создаётся **новая жёсткая ссылка** `EuroOfficeNativeHardLinkNoReplace.Create(destination, pending)` внутри **того же каталога `reviewed`**. Это создаёт новую запись каталога без fallback на copy/move, если hardlink поддерживается и конечного файла ещё нет. Если hardlink недоступен/цель существует — операция отказывает.
- После создания конечного имени удаляется **только собственный случайный pending-файл**, а не эталон, карантинная копия или конечная reviewed-редакция. При аварии либо ошибке pending может остаться: он **не является опубликованным документом**, и автоматической очистки чужих/неидентифицированных файлов нет.
- Затем вновь проверяются SHA-256/размер reviewed, эталона и карантинной копии. Неуспех проверки — исключение и ручное расследование без «исправляющего» удаления конечного файла. Возвращается только краткая квитанция с именем, SHA и длиной; права всегда `SyntheticOnly=true`, `WormUpdated=false`, `SaveCompleted=false`, `AuthorizedForPublication=false`, `DurableAcrossPowerLoss=false`.

## Что реально гарантируется и НЕ гарантируется

**Достигается на поддерживающей hardlink локальной ФС в изолированной VM:** отдельное фиксированное имя новой синтетической reviewed-редакции без штатной перезаписи существующей, повторная проверка байтов и отсутствие записи в WORM/пользовательские документы самим методом. Это только *лабораторное* контрольное сохранение.

**Не доказано:** fsync каталога и полная сохранность после power-loss, аппаратная честность WriteThrough, защита от враждебного соседнего процесса/TOCTOU (никакой полноценной `openat2/renameat2` с directory handles здесь нет), неизменяемость конечного файла (hardlink не превращает файл в WORM), гарантированная защита от сетевых bind mounts, идеальная совместимость ISO/IEC 29500/ECMA-376/MS Office, пользовательские права GET, атомарность сетевого WORM. Нельзя считать hardlink write once в смысле хранилища с юридической неизменяемостью.

Нельзя включать для обычных файлов, пути пользователя, общего сервера, SMB, GUP-2, Nextcloud Hub, GET-system или WORM. Запуск допускается только при отдельном `labApproved=true`, после реальной CEF/Qt приёмки предыдущих этапов и в disposable Linux/Wayland VM без секретов/корпоративных монтирований. Отдельная проверка AGPL и требуемых лицензий остаётся обязательной.

## Подготовленные тесты — не выполнялись

- `EuroOfficeSyntheticReviewedSnapshotTests.cs`: положительная синтетическая reviewed-копия, неизменность эталона и карантина, повторная фиксация с тем же session, отказ без разрешения/v2 evidence, изменение исходника/кандидата, отсутствующий синтетический манифест, symlink reviewed.
- `test_synthetic_reviewed_snapshot_contract.py`: default-off/неиспользование в production, манифест и allowlist, `CreateNew`, `WriteThrough`, `Flush(true)`, проверка исходного SHA перед новой directory entry, `CreateHardLink` без fallback `File.Move/Copy/Replace`, права всегда false.
- `scripts/office_acceptance.py`: offline source gate `cef-synthetic-reviewed-snapshot-source-tests`, обязательный ручной gate `eurooffice-gd31j29-synthetic-reviewed-no-replace-hardlink-durability-vm`.
- В будущей VM нужны отдельные сценарии: crash до flush, после flush, после hardlink, во время удаления pending, существующая цель, hardlink не поддерживается, symlink/reparse на каждом сегменте, изменённый манивест/источник/карантин, отказ при внешних concurrent writers, recovery pending **только после дополнительной идентификации**, Windows/Linux особенности FileSystem, чтение финала независимым парсером и реальное Office-roundtrip.

> **Корректировка GD-31J.33 / .NET 10:** API `System.IO.File.CreateHardLink` доступен начиная с .NET 11, поэтому исходный код больше его не вызывает. Это изменение совместимости **не заменяет** реальную компиляцию, VM, power-loss и security-проверки.
