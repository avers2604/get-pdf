# GD-31J.27ba — защита выбора recovery-копии от конкурентных изменений

**Репозиторий:** `avers2604/get-pdf`. **Ветка:** `feature/gd31j27ba-recovery-concurrent-snapshot-guard`, отдельный stacked Draft поверх GD-31J.27az / PR #165. **Ограничение пользователя:** без сборки, запуска Python/MSTest и Windows/Astra/SMB-стенда. `main`, GitHub Actions, GUP-2, WORM и исходные документы не менялись.

## Проблема

В GD-31J.27az `FindLatestWithEnumerator` перешёл на быстрый поиск: первоначально прочитать маленькие JSON-манифесты, отсортировать по `CapturedUtc`, затем применить дорогую SHA-256 + ZIP/XML-проверку только к новым кандидатам до первого валидного.

Но между **предварительной сортировкой** и **полной проверкой** может измениться:
- само поле `CapturedUtc`, `SourcePath` или `Sha256` в уже просмотренном JSON;
- манифест, который при первоначальном чтении был испорчен, а во время проверки сделался валидным;
- набор имён `*.json` (создание нового снимка либо удаление старого);
- OOXML-копия после вычисления SHA-256, но до окончания проверки ZIP/XML.

Без дополнительных условий результат мог бы соответствовать устаревшей версии снимков, хотя отдельный выбранный файл был проверен.

## Реализованная защита

### Повторная сверка состояния каталога

1. Начальная выборка по-прежнему полностью материализуется до сортировки с лимитом `MaxManifestCandidates=4096`; превышение лимита остаётся ошибкой.
2. Предварительные `RecoveryManifest` сохраняются во временном массиве `observations`, включая результаты `null` для неподтверждённых GUID-манифестов. Никакие метаданные не используются для авторизации восстановления или удаления.
3. Перед любым возвратом — **и перед валидным кандидатом, и перед `null`** — вызывается локальная `EnsureSurveyStillValid()`. Функция повторно получает ограниченный список имён, сверяет его размер и состав без доверия к порядку выдачи NTFS/ext4/SMB; проверяет чтением, что начальные значения метаданных всех ранее наблюдавшихся GUID-манифестов не изменились.
4. При обнаружении изменения набора или значимых полей `RecoveryManifest` выбрасывается `InvalidDataException`: **устаревший результат не показывается как окончательный**. Внешний UI/вызывающий код должен интерпретировать это как «проверить не удалось», а не «резервных копий нет».
5. Дополнительно перед возвратом валидного кандидата `CapturedUtc` от полной проверки сравнивается с первоначальным временем, использованным для сортировки. Для незащищённых файлов настоящей конкурентной записи остаются ограничения path-based проверки.

### Проверка изменения OOXML после SHA-256

`ReadValidCopy` после безопасного `FileInfo`/link/size preflight сохраняет длину и `LastWriteTimeUtc`, вычисляет SHA-256 и при совпадении выполняет прежнюю обязательную проверку ZIP/XML. Затем повторно читает атрибуты: если файл пропал, стал ссылкой, изменил длину или время записи, кандидат отклоняется.

Только для детерминированного синтетического теста добавлены **внутренний** `ReadValidCopyWithPostHashMutation(sourcePath, manifestPath, afterHash)` и необязательный `Action<string>? afterHash = null` у приватного валидатора. В production метод `FindLatest` вызывает стандартный путь **без** callback. Обратного обхода SHA или ZIP нет.

**Важно:** метаданные длина/mtime не доказывают идентичность файла. Злонамеренная замена на такой же по длине файл с восстановленной отметкой времени либо изменение файла между последней проверкой и использованием результата всё ещё потенциально возможно. Для строгой защиты необходим handle-bound протокол открытия с безопасным `FileShare`, файловой идентичностью / OS-дескрипторами и оценкой семантики POSIX/SMB. Это **не реализовано** и не заявляется.

### Цена защиты

Повторно читаются имена манифестов (максимум 4096) и небольшие JSON (~2 КиБ на файл). При обычных трёх retained копиях дополнительная работа мала относительно SHA/ZIP, но **измерений времени не было**. На медленных SMB и слабых ПК стоимость повторных перечислений обязательно измерить позже; пока это консервативный компромисс ради отказа от недостоверного результата. Манифесты, которые при обоих чтениях остаются невалидными и дают `null`, не сравниваются побайтно. Любая смена `null` на валидные поля или обратно вызывает ошибку.

## Новые тестовые сценарии (написаны, НЕ запускались)

В `tests/GetDocument.Office.Tests/OfficeRecoveryFastSelectionTests.cs` четыре дополнительных C# MSTest (теперь **7**):

1. `ChangedManifestTimestampDuringValidationFailsClosed`: во время тестового verifier изменяется время JSON текущего снимка — поиск должен закончиться `InvalidDataException`, файлы остаться.
2. `InvalidManifestBecomesValidDuringVerificationFailsClosed`: JSON старого кандидата из повреждённого превращается в корректный — нельзя вернуть результат старого ранжирования.
3. `NewManifestAddedDuringVerificationFailsClosed`: во время проверки добавляется новый `*.json` — поиск не возвращает устаревший выбор.
4. `CopyChangedAfterHashMustNotBeAccepted`: тестовый callback добавляет байты после SHA перед ZIP — новый валидатор должен отвергнуть изменившуюся копию и не трогать исходник/манифест.

В `scripts/tests/test_recovery_concurrent_selection_contract.py` написаны **8** Python source-only проверок порядка операций, ограничения количества файлов, повторной сверки каталога и манифестов, контроля размера/mtime, регрессий и неизменности прав доступа. Прежний `test_recovery_fast_selection_contract.py` обновлён на 7 C# тестов.

Новый этап регистрируется в `scripts/office_acceptance.py` **до NuGet restore**. `scripts/tests/test_recovery_chain_consistency.py` проверяет регистрацию и уникальность ручных гейтов. В `scripts/tests/test_office_acceptance.py` два ручных пункта остаются `not-run`:

- `gd31j27ba-recovery-concurrent-windows-ntfs-manual-e2e`;
- `gd31j27ba-recovery-concurrent-astra-smb-manual-e2e`.

`releaseReady=false`; новые функции удаления, автоматического исправления, восстановления из недоверенного файла и облачной синхронизации **не добавлялись**.

При обнаружении незавершённого/конкурентного изменения не показывать пользователю «копий нет».
