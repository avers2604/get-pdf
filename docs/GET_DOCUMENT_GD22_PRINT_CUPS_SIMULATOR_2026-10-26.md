# GD-22 — локальные интеграционные пробы печати с имитацией CUPS, драйверные проверки и квитанции очереди

**Дата:** 26.10.2026. **Основа:** GD-21 / PR №46. **Статус:** Draft, не сливать до локальной сборки и аппаратной приёмки.

## Что исправлено и почему

### 1. Настоящий transport smoke без настоящего принтера

Добавлен отдельный проект `tests/GetDocument.Printing.Tests`, с доступом только к внутреннему `GetDocument.Desktop.Printing.LocalPrintBroker`. Его тесты на Linux временно помещают три исполняемых POSIX-имитатора в начало `PATH` **только тестового процесса**:

- `lpstat`: существующая `GET_SIMULATOR`, системный принтер по умолчанию, сценарий исчезнувшей очереди;
- `lpoptions`: `InputSlot`, `print-color-mode`, `PageSize`, `Duplex` с переключаемым списком реально объявленных возможностей;
- `lp`: сохраняет точный аргументный вектор в файл, возвращает идентификатор задания либо имитирует ненулевой код завершения / отсутствие квитанции.

Тестируются **реальные вызовы `LocalPrintBroker`**, включая обнаружение устройств, параметры лотков, наличие поддерживаемого режима, проверку SHA-256 приватной копии, формирование `-P`, `media`, `number-up`, предупреждение о неоднозначном результате и отсутствие обращения к `lp` при отказе. Нет shell-конкатенации аргументов: production использует `ProcessStartInfo.ArgumentList`.

Никакая реальная очередь или сеть не вызывается, поскольку все три команды подменены в отдельном тестовом окружении. После проверки переменные среды возвращаются; папка с имитаторами удаляется. Тестовый класс не допускает параллельных запусков. В Windows тесты этого класса сообщают `Inconclusive`, а не подменяют Windows PrintWorker фиктивным CUPS.

### 2. Отказ от недоказанной поддержки A3/дуплекса в Linux

До GD-22 CUPS проверял существование очереди, выбранный лоток и цветность, но **не проверял фактическую поддержку A3 и дуплекса**. Драйвер мог незаметно перенаправить формат/режим.

`CupsDeviceCapabilities.Supports` читает `lpoptions -p <queue> -l` и распознаёт:
- PPD `PageSize: A4/A3`, IPP `media: iso_a4_210x297mm / iso_a3_297x420mm`;
- IPP `sides: two-sided-long-edge / two-sided-short-edge`;
- legacy PPD `Duplex: DuplexNoTumble / DuplexTumble`.

Для явно выбранного A3/двустороннего режима отсутствие подтверждения блокирует отправку `lp`. Если драйвер объявляет размер листа, выбранный A4 также проверяется по этому списку. По умолчанию при недоступных опциях допускается только A4 + односторонняя печать; все явно повышенные возможности требуют фактического объявления. В CUPS брокер теперь **один раз** запрашивает параметры выбранной очереди для совместной валидации бумага/дуплекс/лоток/цвет. Эти варианты остаются запросами к локальному драйверу — конкретную физическую комбинацию «A3 в лотке №2» дополнительно проверять на реальном МФУ.

### 3. Проверяем приём в очередь, а не только exit code

Раньше процесс `lp` с `exit 0` приводил к сообщению «задание передано» независимо от его вывода. Теперь `PrintSubmissionReceipt.CupsJobId` требует строгую строку `request id is <ожидаемый_принтер>-<числовой_ID> (1 file(s))`; задание с некорректным номером, другой очередью, лишними строками или пустой квитанцией считается **неопределённым**, а не подтверждённым. Для `lp/lpstat/lpoptions` язык вывода принудительно `LC_ALL=C`.

Windows headless worker продолжает использовать существующую строку `submitted`, но `LocalPrintBroker` теперь проверяет **точный маркер**. Ненулевой exit code классифицируется прежней моделью; `exit 0` без ACK — неопределённое завершение.

Положительный ответ означает только **принятие очередью**; не факт, что принтер физически распечатал все листы. Неизвестный исход по-прежнему блокирует повторы в той же вкладке, чтобы не создать двойной тираж.

## Запуск локально без принтера

На Linux (включая Astra Linux, при установленном .NET 10 SDK и офлайн NuGet cache):

```bash
bash scripts/verify-get-document-cups-simulator.sh
```

Полная проверка проекта:
```bash
bash scripts/verify-get-document-linux.sh
```

Для Windows локальные сборка и тесты:
```powershell
pwsh -File scripts/verify-get-document-windows.ps1
pwsh -File scripts/windows-build-get-document.ps1
```

Тестовый проект добавлен в `GetDocument.slnx`, Windows- и Linux-скрипты проверки. GitHub Actions не включаются. Не добавлены новые runtime-пакеты; используется текущий .NET 10/MSTest и существующие компоненты.

## Новые проверки

- `LocalCupsSimulatorTests`: обнаружение очереди, default, лотки, точные argv, правильный output range, 4-up, A3/duplex yes/no, неправильный лоток/цвет, исчезнувшая очередь, отмена, изменённый SHA, `lp` failure и отсутствие квитанции;
- `CupsDeviceCapabilitiesTests`: PPD A3, IPP media/sides, старый DuplexNoTumble/Tumble, пустые и некорректные данные;
- `PrintSubmissionReceiptTests`: receipt только от выбранной очереди с цифровым job ID, вывод с посторонними данными, точный ACK Windows.

## Что проверено в этой среде

- POSIX shell-имитаторы проверены локально через `sh -n` и запуск в отдельном временном каталоге: queue discovery, lpoptions, аргументы, режим без номера задания, отказ `lp`. **Это успешная проверка самих имитаторов, не C#-тестов.**
- `.NET 10 SDK` в доступной среде отсутствует, поэтому restore/build/MSTest для GD-22 **не запускались**. Встроенный Windows spooler/CUPS и физические МФУ также недоступны.
- GitHub может подтвердить отсутствие merge conflicts, но это не доказательство компиляции/корректности печати.

## Обязательная аппаратная приёмка

1. Windows PrintWorker на реальных HP/Canon/Bulat/Катюша: доступные A4/A3, simplex/duplex, лоток, проверка верного SHA-256 и корректного WPF/XPS print ticket.
2. Astra Linux CUPS с PPD и IPP Everywhere, в том числе неизвестный `PageSize`, устаревший `ColorModel` и печать из недоступного сетевого принтера.
3. Положительный ACK, неответившая служба, выключенный принтер, остановленное задание, физическое число листов, двойное подтверждение и послеаварийное восстановление.
4. DOCX/XLSX/PPTX из встроенного Office, несохранённые изменения, кириллица, PDF-превью, выбор диапазона и печать без сохранения исходного WORM.
5. Принимать в `main` только после успешной компиляции/MSTest на локальных системах и физической приёмки. Отдельная ветка Euro-Office №42 остаётся несвязанной до готовности серверного trusted export-to-PDF.
