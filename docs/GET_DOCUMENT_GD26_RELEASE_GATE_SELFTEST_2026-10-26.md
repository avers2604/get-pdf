# GD-26 — проверка самого Release Gate и исправление .NET 10/MTP-скриптов

Дата: 26.10.2026. База: GD-25 / PR №50. Статус: Draft до реальной сборки и запуска.

## Зачем нужен этап

В GD-25 появился релизный контроль, который считывает TRX-отчёты и решает, выполнены ли обязательные тесты. Но *проверяющий модуль сам ранее не проверялся*. Анализ выявил несколько потенциально ложноположительных результатов:

- обязательное имя проверялось через `Contains`: `FakeMyCriticalTest` могло быть принято вместо `MyCriticalTest`;
- корневой XML мог быть каким угодно, если содержал `UnitTestResult`;
- отсутствовала сверка `ResultSummary/Counters` с фактическими результатами;
- `ResultSummary outcome="Failed"` сам по себе не блокировал отчёт;
- один `Passed` при другом `Inconclusive` для того же критического теста проходил проверку;
- чтение TRX не задавало отдельного ограничения объёма XML и запрета DTD.

GD-26 вводит независимую самопроверку и строгий разбор отчётов, **не требует реального принтера для тестирования самого решающего алгоритма**.

## Добавленные компоненты

### 1. ReleaseReportEvaluator.cs

- Допускается только стандартный TRX XML namespace `http://microsoft.com/schemas/VisualStudio/TeamTest/2010` с корнем `TestRun`, разделами `Results` и `ResultSummary/Counters`.
- Ограничение файла 32 МиБ и XML reader с запретом DTD/внешнего разрешения сущностей. XML с внешними ресурсами не обрабатывается.
- Счётчики `total`, `passed`, `failed` должны соответствовать `UnitTestResult`. Несогласованный отчёт или неизвестный статус теста блокирует допуск.
- Критический тест распознаётся по точному имени метода (либо полному квалифицированному имени, заканчивающемуся точным `.MethodName`), а не по вхождению подстроки.
- Все записи одного обязательного теста должны иметь статус `Passed`; хотя бы один `Inconclusive`/`Skipped`/`Failed` блокирует этот критический тест.
- Каждый обязательный набор тестов должен содержать минимум один `Passed`, не иметь проваленных тестов и ошибок формата.
- Несуществующие, битые и превышающие ограничения TRX помечаются как ошибки проверки, не как успех. Учитывается платформа Linux/Windows при выборе обязательных тестов.

### 2. ReleaseGateSelfTests.cs

`GetDocument.ReleaseGate --self-test` выполняет в памяти набор независимых сценариев на искусственных TRX, включая нормальный отчёт, отсутствующие критические тесты, поддельное имя, `Inconclusive`, неоднозначные дубликаты, неизвестные статусы, внутренние сбои, неверные счётчики, пустой и повреждённый отчёт и XML с DTD. Выдаёт ненулевой exit code при любом нарушенном утверждении.

Скрипты GD-25 теперь **выполняют эту самопроверку до обработки настоящих TRX**. Она не нуждается ни в физических принтерах, ни в серверном Euro-Office, но для компиляции и запуска необходим установленный .NET 10 SDK.

### 3. Формирование доказательства готовности

Основной `Program.cs` использует только `ReleaseReportEvaluator` и пишет `get-document-release-gate.json` сначала во временный файл того же каталога, затем атомарно перемещает его по целевому пути. Таким образом, оборвавшийся процесс не оставляет наполовину записанное решение `Approved=true`.

### 4. Исправление команд `dotnet test` для .NET 10 MTP

В `global.json` активен `Microsoft.Testing.Platform`. По современной модели `.NET 10` тестовый проект явно указывается через **`dotnet test --project <test.csproj>`**. Исправлены все основные Windows/Linux-скрипты, включая базовую проверку, закрытую NuGet-приёмку, релизный запуск и CUPS simulator.

Для MTP расширение TRX по-прежнему вызывается через `--report-trx --report-trx-filename ... --results-directory ...`. Если фактический SDK/MSTest profile не регистрирует расширение, запуск должен завершиться ошибкой и релиз остаётся заблокирован.

Официальная документация:
- https://learn.microsoft.com/en-us/dotnet/core/testing/unit-testing-with-dotnet-test
- https://learn.microsoft.com/en-us/dotnet/core/testing/unit-testing-platform-extensions-test-reports

## Команды локальной проверки

Прямая самопроверка после локального офлайн build:

```bash
dotnet run --project tools/GetDocument.ReleaseGate/GetDocument.ReleaseGate.csproj -c Release --no-build --no-restore -- --self-test
```

Полная Linux/Astra приёмка:

```bash
bash scripts/verify-get-document-release-linux.sh /srv/get/nuget-feed
```

Windows (PowerShell 7):

```powershell
pwsh -File scripts/verify-get-document-release-windows.ps1 -OfflineNuGetFeed 'D:\GET\NuGetOffline'
```

Оба скрипта сначала выполняют строго офлайн-сборку, затем самопроверку GD-26, затем реальные MSTest с TRX и отдельное решение `Approved`. Отчёты остаются в каталоге пользователя, без облачной отправки.

## Ограничения и решение по релизу

**Ни один новый C# self-test фактически не запущен в данной среде:** в исполнителе отсутствуют `dotnet`, `csc`, `pwsh`, `mono`. Код и скрипты внесены в GitHub, но не собраны. Поэтому:
- не утверждается, что self-test 100% прошёл;
- не утверждается, что формат TRX каждого реально используемого пакета уже согласован с новым парсером — это должно подтвердиться на Windows/Astra;
- проверки реальных Office-процессов, WORM, бумажного тиража A3/A4, дуплекса, лотков и CUPS продолжают требовать физической приёмки;
- самопроверка не заменяет независимую проверку целостности и происхождения тестовых отчётов, пакетов NuGet, подписей и экземпляра исходного кода.
