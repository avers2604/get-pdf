# GD-31J.27az — сокращение числа ZIP/SHA-проверок в поиске recovery-копий

**Репозиторий:** `avers2604/get-pdf`; **ветка:** `feature/gd31j27az-recovery-fast-verified-selection`, stacked Draft поверх GD-31J.27ay / PR #164. Сборка .NET, Python unittest, MSTest, GUI, Windows NTFS и Astra Linux/SMB не выполнялись по решению пользователя. Никаких изменений `main`, GitHub Actions, WORM, GUP-2, исходных документов или EuroOffice-native SaveAs.

## Причина оптимизации

Прежний `FindLatest()` последовательно просматривал все манифесты и для **каждой** подходящей копии вызывал `ReadValidCopy` — сначала полное потоковое чтение ZIP/XML через `EnsureValidPackage`, затем повторное чтение файла для SHA-256. При трёх валидных снимках даже выбор самого свежего мог требовать три разархивирования/проверки XML и три хэширования. На слабых ПК и сетевых накопителях это потенциально дорого.

## Изменения в основном коде

1. **Полная ограниченная регистрация имён:** `FindLatestWithEnumerator` сначала материализует **не более 4097** имён `*.json` через `Take(MaxManifestCandidates + 1).ToArray()`. Если их **больше 4096**, возвращается **ошибка `InvalidDataException`**, а не `null` и не частичный результат. Таким образом, ошибки ленивого перечисления до этой границы также нельзя скрыть, успев вернуть «нет копий».
2. **Дешёвый предварительный отбор:** допускаются только имена с GUID-основой, корректные небольшие JSON-манифесты, нужный `SourcePath` и допустимое время. Кандидаты упорядочиваются по `CapturedUtc` от новых к старым. **Эти метаданные недоверенные** и используются исключительно как подсказка порядка, не как разрешение восстановить или удалить файл.
3. **Подтверждение перед выдачей:** для первого кандидата вызывается прежний `ReadValidCopy(source, extension, path)`, который **заново** читает манифест и проверяет хэш, тип документа, ZIP/XML, ограничения распаковки и отсутствие ссылки. При отказе следующий кандидат проверяется аналогично, пока не найден первый валидный. Это сокращает количество тяжёлых операций при наличии исправной свежей копии, но **не отключает** полную проверку выбранного документа.
4. **SHA перед ZIP, но после безопасной проверки пути:** `ReadValidCopy` сначала проверяет `FileInfo.Exists`, ненулевую длину, предел `MaxCopyBytes=128 МиБ` и `IsLinkedFile`; лишь затем считает SHA. Если хэш не совпадает, дорогая ZIP/XML-проверка не требуется. Если совпадает — `EnsureValidPackage` выполняется как раньше, повторно проверяя тип файла, ссылку, ZIP-пути, макросы, размеры, степень сжатия, XML и недопустимые конструкции.
5. **Нет кэша доверия:** после любого нового обращения к `FindLatest` манифест и файл верифицируются повторно. Ни предварительная сортировка, ни время изменения файлов, ни прежний положительный результат не заменяют проверку.

`Prune` и `Discard` сознательно **не оптимизировались аналогично**: они проверяют все пары, которые могут удалять, и сохраняют копия→манифест с консервативным отказом при ошибках. Ограничитель 4096 применяется **только к FindLatest**, не даёт полномочий очистки. Реальные тесты времени загрузки не проводились, поэтому численное ускорение не заявляется.

## Написанные синтетические регрессии

В `tests/GetDocument.Office.Tests/OfficeRecoveryFastSelectionTests.cs` добавлены **3 MSTest**:

- `NewestValidSnapshotIsTheOnlyOneFullyVerified`: синтетические валидные DOCX и внутренний делегат подсчёта проверок; при исправном новейшем кандидате старый не должен подвергаться дорогостоящей проверке.
- `FailedNewestVerificationFallsBackToOlderVerifiedCopy`: если проверка более новой копии не пройдена, поиск переходит к старой и возвращает её.
- `TooManyManifestsFailsClosedBeforeReadingAnySnapshot`: 4097 имён, без создания реальных архивов, дают `InvalidDataException` до верификации любой копии.

В `scripts/tests/test_recovery_fast_selection_contract.py` — **8 source-only Python проверок**: полное ограниченное перечисление, последовательность сортировки и проверки, повторное чтение манифеста, безопасность SHA-предфильтра, лимиты и отсутствие файловой мутации. Предыдущий `test_recovery_folder_state_contract.py` адаптирован к новому циклу: `ToArray` выполняется до сортировки, а поздняя ошибка перечисления не превращается в «нет копий».

`releaseReady=false`, выпуск запрещён до реальной независимой приёмки.

## Ограничения и риски

- Если свежие кандидаты повреждены, поиск будет проверять их и старые копии последовательно. Сортировка — не гарантия уменьшения работы на каждом конкретном наборе данных.
- Метаданные `CapturedUtc` в JSON не имеют криптографической подписи. При конкурентной модификации между предварительным чтением и окончательной верификацией возможны изменения порядка. Повторная проверка защищает **пригодность возвращаемой копии на момент проверки**, но не обеспечивает атомарной консистентности всех файлов и не устраняет TOCTOU.
- Для 4097+ манифестов ошибка явно сигнализирует о превышении лимита, а не о пустом хранилище. Пользовательские файлы при этом не меняются и автоматически не удаляются.
- Ошибки ACL/SMB во время перечисления не скрываются: `FindLatest` не возвращает неполный результат. Отдельный недоступный/повреждённый JSON по прежнему отклоняется локально; остальные пригодные копии можно искать дальше.
- Тесты с injected verifier проверяют **порядок выбора**, а не реальную производительность декомпрессии. Длительные измерения на слабом Windows 10 ПК и Astra Linux с файлами 1, 32, 128 МиБ остаются отдельной задачей.
