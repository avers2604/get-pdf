# GD-29 — контроль контрактов тестирования перед сборочной приёмкой

**Дата:** 27.10.2026. **База:** интеграционная ветка GD-28 / PR №55. **Статус:** Draft, подготовлено к локальной лаборатории.

## Зачем это нужно

После объединения PR №53 и №54 релизный контроллер `GetDocument.ReleaseGate` требует конкретные тесты с итоговым статусом `Passed`. Если метод был переименован или его MSTest-атрибут удалён, эта несогласованность выявлялась только после полного прогона всех проектов, включая длительные интеграционные проверки.

GD-29 вводит **отдельный ранний аудит исходных тестовых контрактов**. Он не заменяет компилятор и не считает наличие теста доказательством того, что тест прошёл.

## Изменения

- Новый `tools/GetDocument.ReleaseGate/TestContractAuditor.cs`: для каждой обязательной тестовой сборки Windows/Linux определяет каталог проекта, проверяет `.csproj` и ищет требуемый метод, помеченный `[TestMethod]` или `[DataTestMethod]`.
- Допускается точное имя метода; совпадение с другим суффиксом/префиксом не засчитывается. Сканер не учитывает комментарии, строки с упоминаниями атрибута и сгенерированные `obj/bin` файлы.
- `GetDocument.ReleaseGate --audit-contracts <repo-root> <windows|linux>` возвращает ненулевой код и список отсутствующих обязательных тестов. Положительный результат сообщает **только о наличии объявлений**, не о компиляции и не об успешном выполнении.
- Обе команды лаборатории `verify-get-document-release-{linux,windows}` запускают аудит после `--self-test` и до создания/чтения TRX.
- В `ReleaseGateSelfTests` добавлены сценарии «атрибут в комментарии», «атрибут в C# строке», «настоящий атрибут с `Timeout` между ним и методом» и подмена имени.

## Что проверено статически через GitHub

Были получены реальные исходники интеграционной ветки, сверены **11 обязательных имён тестовых методов** в Core, Printing и Office. Все 11 деклараций найдены в ожидаемых файлах; `tests/GetPdf.Tests/GetPdf.Tests.csproj` также существует.

Это **не означает**, что C# проекты собираются, что MSTest запустился, что тесты Passed, что принтер физически распечатал документ или что Euro-Office готов к защищённому внедрению.

## Команды локального запуска

Сначала полностью офлайн подготовить SDK и зависимости и собрать ReleaseGate с `.NET 10`. После этого проверить только исходники:

```bash
dotnet run --project tools/GetDocument.ReleaseGate/GetDocument.ReleaseGate.csproj -c Release --no-build --no-restore -- --audit-contracts . linux
```

```powershell
dotnet run --project tools/GetDocument.ReleaseGate/GetDocument.ReleaseGate.csproj -c Release --no-build --no-restore -- --audit-contracts . windows
```

Полный сценарий `Windows / Astra Linux`:

```bash
bash scripts/verify-get-document-release-linux.sh /srv/get/nuget-feed
```

```powershell
pwsh -File scripts/verify-get-document-release-windows.ps1 -OfflineNuGetFeed 'D:\GET\NuGetOffline'
```

Все команды используют существующие правила закрытого контура; никаких GitHub Actions не добавлено. Отчёты остаются в личном каталоге пользователя.

## Блокеры первой рабочей сборки

1. В доступной среде **нет `dotnet`/C# компилятора**, поэтому GD-29 невозможно достоверно назвать сборкой, прошедшей MSTest. Новый Source Contract Audit и `--self-test` написаны, но не выполнены.
2. Требуется реальное выполнение `dotnet restore/build/test` на Windows 10/11 и Astra Linux. Любая найденная ошибка исправляется отдельным контролируемым изменением до возобновления тестирования.
3. После компиляции остаются обязательные реальные проверки печати A4/A3, duplex, input trays, 1/2/4-up, WORM и документа Office с несохранёнными изменениями. Принятие в очередь не означает печать.
4. Перед merge в `main` нужно учесть шесть собственных коммитов текущей главной ветки; Euro-Office PR №42/52 подключать только после проверки его защищённого revision-bound export-to-PDF.

**Релиз не подтверждён.** PR оставить Draft, `main` и WORM-оригиналы не менять.
