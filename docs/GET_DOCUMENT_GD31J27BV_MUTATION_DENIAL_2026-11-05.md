# GD-31J.27bv — fail-closed устранение опасного удаления по имени

Дата: 2026-11-05. Base: GD-31J.27bu, Draft PR #186. **Статус: Draft, `releaseReady=false`, без компиляции и платформенных испытаний.**

## Почему это P0

Текущая `OfficeRecoveryStore.ReadValidCopy` проверяет SHA-256/ZIP с удерживаемым stream и перепроверяет метаданные имени после чтения. Но последующее `Discard` / `Prune` раньше вызывало `File.Delete(path)` через отдельный `FileInfo` preflight. Подмена между проверкой и удалением не исключена: File ID удерживаемого stream не обязательно соответствует объекту, который будет удалён по **имени**.

Реальные native-инструменты из BR–BU пока диагностические и не доказывают writer isolation / проверенную привязку *имени к открытому родительскому дескриптору*. Поэтому оставлять продукционное удаление по пути нельзя.

## Реализовано

1. **Рабочие `OfficeRecoveryStore.Discard` и `Prune` стали строго недеструктивными**. После сохранения оригинального документа копии и манифесты сохраняются. `Prune` больше не вызывает `DeleteVerifiedPair`; `Discard` не перечисляет файлы для удаления. Даже повторное включение отдельной настройки не должно запустить старый путь удаления.
2. Старый `TryDeleteVerifiedPart` с `FileInfo + File.Delete` **удалён**. `OfficeRecoveryStore.TryDelete` без явно переданного **тестового** delegate теперь ничего не удаляет; делегат остаётся только для синтетических fault-injection тестов. `DeleteVerifiedPair(copy,manifest,delegate)` остаётся как внутренний **тестируемый контракт порядка** (сначала копия, потом манифест), но из рабочих `Discard/Prune` более не вызывается.
3. Добавлен `RecoveryPairMutationGate` — **denial-only** аудит пары из трёх существующих caller-owned `SafeFileHandle` (parent/copy/manifest) и двух повторных чтений идентичностей copy/manifest. Диагностика отвергает неполные идентификаторы, alias copy/manifest, разные тома и нестабильные File ID. Даже при идеальных синтетических флагах результат только `NeedsNativeBoundOperation`, а `CanAuthorizeNativeMutation=false`; оба пути `CanDeleteByPath=false`, `CanPublishByPath=false`. Родительский handle при этом ещё не сертифицирован, и имя **не** привязано к нему.
4. Пока безопасная очистка недоступна, `CaptureAsync` до вызова экспортёра проверяет количество уже опубликованных **GUID.json** манифестов в каталоге одного источника. Достигнут лимит **32** → новая копия не создаётся, старые не удаляются, возвращается явная ошибка. Это контроль накопления, а **не квота байтов и не доказательство безопасности перечисления**. Дополнительно остаётся существующая проверка давления на том и backlog незавершённых файлов.
5. Обновлены регрессии в `OfficeRecoveryStoreTests.cs`: после подтверждённого Save данные остаются на месте; пять копий теперь сохраняются (раньше тест ожидал три); тестовые оригиналы не изменяются.
6. Добавлены **12 MSTest** на модель пары, запрет pathname-действий, подмены File ID, разные тома, закрытые дескрипторы и admission budget; **9 source-only Python contract tests** с проверкой отсутствия рабочих вызовов удаления.

## Совместимость и существенное изменение поведения

- После успешного Save `Discard` больше **не освобождает диск** и не скрывает старую аварийную копию из `FindLatest`, если она всё ещё валидна. Пользовательский интерфейс и подсказки не должны обещать, что такая копия удалена.
- Целевое удержание **3 копий** временно выключено. Доступ к новым снимкам может быть остановлен после **32** записей одного документа. Это сознательный компромисс между риском удаления чужого файла и риском накопления. **Удаление руками** возможно только по согласованной процедуре администратора после резервного копирования и проверки владельца; приложение не предлагает автоматическую очистку.
- `CaptureAsync` всё ещё использует `File.Move(temporaryCopy, finalCopy)` и `File.Move(temporaryManifest, finalManifest)`. **ЭТАП НЕ УСТРАНЯЕТ ВСЕ TOCTOU-ГОНКИ ПУБЛИКАЦИИ**; рабочее включение Native SaveAs/WORM остаётся блокировано. `FindLatest` и чтение манифеста тоже имеют path-based ограничения, хотя делается SHA/ZIP-проверка.
- Для восстановления безопасной автоматической очистки потребуется независимая native реализация: Windows parent-directory handles и owner/token ACL, Linux relative `unlinkat`/аналог безопасного протокола, имя/identity bound checks, lock до конца операции, negative race injections, safe cancellation, cross-process/SMB review, журнал происхождения и результаты реальных OS тестов. Простого повторного `FileInfo.Refresh` недостаточно.

## Приёмка

Зарегистрированы **4 новых обязательных ручных gates**, все `not-run`:

- `gd31j27bv-windows-ntfs-delete-denial-manual-e2e`: сохранение исходника и копий после Save, отсутствие удаления в Windows, ACL/junction/rename.
- `gd31j27bv-astra-ext4-delete-denial-manual-e2e`: отсутствие unlink после Save, uid/mount/links, отмена и перераспределение fd.
- `gd31j27bv-smb-concurrent-replace-denial-manual-e2e`: подмена сетевых путей и отказы, отсутствие удаления посторонних файлов.
- `gd31j27bv-retention-disk-budget-manual-e2e`: 31/32 копии, отказ нового экспорта на лимите, ENOSPC и обычное повторное открытие.

Каталог `MANUAL_GATES` теперь содержит **149 пунктов**. Все новые source-only tests зарегистрированы до offline NuGet restore, CI/Actions не включались. Код, тесты и документация записаны в ветку.

Проверка в данной сессии: GitHub read-back/структурные предикаты. **Не выполнялись C# build, MSTest, Python unittest в репозитории, Windows/Astra/SMB E2E, симуляции power loss, nor native API attestation.** Изменения нельзя считать выпущенными.
