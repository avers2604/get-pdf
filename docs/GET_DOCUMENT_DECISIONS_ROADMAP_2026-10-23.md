# ГЭТ Документ — решения и дорожная карта

**Дата:** 23.10.2026  
**Статус:** зафиксированные продуктовые решения + план, не отчёт о завершённой реализации.  
**Базовый репозиторий:** [avers2604/get-pdf](https://github.com/avers2604/get-pdf)

> **Главное утверждённое правило.** При выборе библиотек и редакторных движков первичны **максимальная функциональность и совместимость с Microsoft Office (Word, Excel, PowerPoint)**. **Весь пользовательский интерфейс — собственный, в стиле ГЭТ**; **реализация — source-first: переиспользовать существующие исходники и библиотеки прежде, чем писать новый функциональный код**, поэтому готовый внешний вид стороннего редактора не является критерием выбора. При этом лицензионная допустимость и информационная безопасность обязательны.

## 1. Реестр решений

| Направление | Зафиксированное решение |
|---|---|
| Архитектура | Единое приложение «ГЭТ Документ»: самостоятельная Avalonia-оболочка, кроссплатформенное Core-ядро и заменяемые адаптеры движков. |
| Лаунчер | Создать документ Word, таблицу Excel, презентацию, открыть файл; сканирование подключить позднее. |
| Вкладки | PDF, DOCX, XLSX, PPTX и изображения открываются **в одном окне** с общими вкладками. |
| UI / UX | Единый оригинальный стиль ГЭТ, собственные панели и команды; брендбук ГЭТ учитывать при финализации. |
| Функции | Максимально приблизиться к возможностям Microsoft Office. Принимать решения по таблице проверенных функций и реальных тестовых документов. |
| Движки | Не привязываться к одной библиотеке. Основной функциональный кандидат — LibreOffice; ONLYOFFICE и Collabora Online — обязательные сравнительные прототипы; ProEdit — вариант лёгкого редактирования после проверки зрелости. |
| Таблицы | ExcelDataReader использовать для чтения, **не** считать полноценным Excel-редактором. Полноценное редактирование — через выбранный офисный движок. |
| PDF | Сохранить возможности «ГЭТ PDF»: просмотр, выделение, печать, формы, подписи, редактирование в рамках доступных операций. |
| Шаблоны | Scriban + OOXML, корпоративные формы — после утверждения образцов. |
| Изображения | Адаптеры NetVips / OpenCvSharp после проверки native-зависимостей; обрезка, поворот, TIFF, улучшение качества и пакетная обработка. |
| Сетевые файлы | Существующий Windows Server 2016, SMB/ACL под текущим пользователем; позднее Linux/Samba, без второго хранилища; конфликты, отслеживание изменений, версии. |
| Документооборот | Защищённая интеграция с GUP-2; контроль ревизий, целостность, аудит; WORM-оригиналы не изменять. |
| Сканирование | Поздняя интеграция с самостоятельным «ГЭТ Сканирование», без переписывания драйверов/модулей. |
| Пасхалка | «Онлайн Дурак» после 10 нажатий в специальной области. Изолировать от рабочих документов, следовать политике закрытой сети. |
| Среда | Windows + Linux, включая отечественные дистрибутивы, адаптивный DPI и работоспособность на слабых ПК. |
| Лицензирование | Использовать открытые компоненты при выполнении лицензий и уведомлений; проверять GPL/AGPL отдельно. Внутренняя установка сама по себе не отменяет авторских прав. |
| Версии и рецензирование | История редакций, восстановление, комментарии, сравнение изменений и конфликты с правками через Проводник/SMB. |
| Локальные интеллектуальные средства | Классификация и проверка документов, предложения OCR, контроль качества и проверка перед отправкой без обязательного интернета. |
| GET-system | Будущая интеграция только через контракты/заглушки; GET-system и GUP-2 — разные проекты; отдельную веб-версию пока не создавать. |
| Проверки | Сборки, тесты, UI и проверки совместимости выполнять локально; GitHub Actions не включать, черновые PR не считать готовым релизом. |

## 2. Сравниваемые технологии

| Технология | Роль | Что требуется подтвердить |
|---|---|---|
| LibreOffice Writer/Calc/Impress | Главный функциональный кандидат для DOCX/XLSX/PPTX | Реально доступные функции через UNO / LibreOfficeKit, стабильность отдельного процесса, экспорт и интеграция со своим UI |
| ONLYOFFICE Docs | OOXML-совместимость и совместное редактирование | Локальная инфраструктура, API, функциональные ограничения и условия AGPL/коммерческих сборок |
| Collabora Online | Совместная работа и серверный офисный редактор | Особенности встраивания, лицензирование сборки и производительность |
| ProEdit | Лёгкий встроенный редактор | Уровень поддержки сложных документов, лицензия конкретного проекта, зрелость |
| Avalonia | Собственный UI, лаунчер, вкладки | Рабочая сборка на Windows/Linux, DPI, удобство работы на старых ПК |
| Scriban + Open XML SDK | Шаблоны и генерация OOXML | Round-trip, безопасность шаблонов, права на официальные формы |
| ExcelDataReader | Импорт/чтение XLS/XLSX/XLSB | Не использовать для полноценного редактирования |
| NetVips / OpenCvSharp | Работа с изображениями | Зависимости, форматная совместимость, безопасность |
| GET PDF Core | Просмотр/редактирование PDF | Отсутствие регрессий и безопасная печать/подписи |

**Архитектурный принцип:** Shell → общее пространство вкладок и команд → интерфейсы адаптеров текста, таблиц, презентаций, PDF, изображений → соответствующие движки. Права, версии, аудит и интеграция GUP-2 — сквозные сервисы. Не следует считать, что произвольную функцию движка можно автоматически вывести на свой UI: у каждого действия необходим рабочий API/контракт или отдельная реализация.

## 5. Порядок следующего шага

1. Уточнить реальное содержимое main, веток и PR; убрать дубли и разрешить зависимости без преждевременного merge.
2. Запустить локальные restore/build/test, UI-smoke и тесты на Windows/Linux. GitHub Actions пока не использовать.
3. Сделать параллельный прототип редакторных движков и заполнить матрицу совместимости с Microsoft Office.
4. Выбрать функционально самый сильный интегрируемый стек по форматам и подтвердить лицензирование, API и безопасность.
5. Отразить решения в последующих PR, сохранять обновляемый реестр функций и известные ограничения.

## 7. Сквозные функции, которые должны оставаться в плане

- **Одно окно** с постоянной вкладкой «Главная», верхней полосой документов различных форматов, дедупликацией открытого файла, сохранением несохранённых правок и будущей интеграцией отдельного приложения «ГЭТ Сканирование». Приложение сканирования остаётся самостоятельным; драйверы не переносить в офисное ядро.
- **Собственный фирменный интерфейс ГЭТ** по официальному брендбуку: официальные изображения и шрифты, светлая тема, DPI, слабые ПК, работа на нескольких мониторах. Не копировать сторонний интерфейс LibreOffice/ONLYOFFICE «как есть».
- **Office без потери данных:** редактирование, таблицы, стили, рецензирование, графики, презентации, макеты, поля, формулы, диаграммы; если используемый API не предоставляет функцию, отмечать её как недоступную, а не имитировать.
- **PDF:** просмотр с выделением текста, печать, формы, подписи, аннотации, черновики и многофайловая работа. Функции WPF не считать перенесёнными в Avalonia, пока не выполнен end-to-end тест.
- **Корпоративные документы:** централизованные шаблоны после утверждения, история редакций, комментарии, защита от одновременного сохранения и изменений через Проводник, предпросмотр.
- **Файлы:** существующий Windows Server 2016, позже Linux/Samba и сохранение действующих прав доступа. Никаких вторых файловых серверов, общих паролей пользователей, внешнего интернета или автоматического сбора всего сетевого ресурса.
- **GUP-2, не GET-system:** одно действие открытия PDF, безопасная авторизация, возврат **новой** редакции, проверка целостности и аудит, неизменяемые WORM-оригиналы. GET-system — отдельный будущий интеграционный контур со stub-контрактами.
- **Локальные интеллектуальные функции:** оценка качества сканов/изображений, определение потребности в OCR, контроль метаданных, проверка полей и конфиденциальной информации. Локальные модели запускаются на допустимой инфраструктуре закрытой сети; нет автоматической передачи документов в публичное облако.
- **Скрытый «Дурак»:** 10 последовательных нажатий на официальный знак открывают внутреннюю вкладку. Реальный многопользовательский режим — только с разрешённым внутренним сервером, не со скрытыми внешними сетевыми подключениями. Игровой сервер пока отсутствует.
- **Платформы и поставка:** Windows — первый выпуск; ядро, файловые адаптеры и оболочка — кроссплатформенные с первого дня; совместимость Astra Linux, Альт и РЕД ОС подтверждать на конкретных версиях, включая зависимости PDFium, SkiaSharp, LibreOffice и печать CUPS.
- **Лицензии:** точный аудит MIT/BSD/GPL/AGPL/коммерческих SDK, исходных библиотек и условий собственного UI/перераспространения. Никаких заведомо платных компонентов в обязательной установке.

## 12. Обязательное правило разработки: SOURCE-FIRST / REUSE-FIRST

**Утверждённое решение:** максимум уже существующего рабочего кода, минимум дублирования и самостоятельного повторного изобретения функций. Это правило применяется ко всем GD-01–GD-10 и последующим этапам и не отменяет главного требования — максимально близкой функциональности и совместимости с Microsoft Office.

**Последовательность для каждой функции:**
1. Проверить **наши** существующие исходники и открытые PR (в первую очередь `GetPdf`, `GetDocument.Core`, `GetDocument.Office`, `GetDocument.Desktop`; затем совместимые части отдельных ГЭТ приложений) и найти работающее решение. Повторно не писать уже имеющийся код.
2. Проверить готовый поддерживаемый проект / библиотеку из внешнего репозитория; использовать пакет как зависимость, а исходники адаптировать и форкать только при конкретной технической необходимости. Не переписывать целый движок для получения собственного UI.
3. Проверить фактический API нужной функции, round-trip документов, тесты, безопасность, влияние на RAM/CPU, работу офлайн и нативные зависимости на Windows/Linux.
4. Зафиксировать источник (репозиторий, commit/tag, версию, лицензию, copyright/NOTICE), ограничения лицензирования, интеграционный способ и причину выбора в PR. **Нельзя автоматически копировать любой код из Интернета:** авторские права, GPL/AGPL, условия форков и поставки проверяются до включения.
5. Создавать **только недостающий glue-код**: платформенные адаптеры, абстракции, интеграции, тесты, проверки целостности/ACL, безопасность, UI ГЭТ. Собственную реализацию функционального движка допускать лишь если готовое решение не подходит и причина задокументирована.
6. Обязательно проверять локально, без GitHub Actions: restore/build/test, Windows/Linux GUI, реальные файлы Office, сложные PDF, сетевые отказные сценарии. Наличие пакета в NuGet или кода в PR не доказывает готовности.

### 12.2. Условие любого нового PR

PR по функциональности должен отвечать на четыре вопроса:
- **Что нашли готового** внутри нашего проекта и во внешних исходниках?
- **Почему выбрали** эту библиотеку или реализацию, какие функции реально доступны через API?
- **Что остаётся написать самим** и почему нельзя просто переиспользовать готовое?
- **Как подтвердили** право использования, офлайн-работу, Windows/Linux, качество форматов, безопасность и регрессии?

Для функциональных модулей предпочтителен **адаптер поверх поддерживаемого стороннего движка** вместо локального форка. Форк допустим, если требуется патч/доработка, версионирование и обслуживание подтверждены. Внешний код нельзя бездумно встраивать целиком: минимизировать цепочки зависимостей, исключать неподходящие лицензии и уже существующие функции.

**Особенно для Office:** приоритет качества и функциональности выше минимального количества строк; source-first нужен для сокращения сроков и числа дефектов, а не для упрощения продукта или ухудшения совместимости.
